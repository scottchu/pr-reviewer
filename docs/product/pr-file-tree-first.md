# PR file groups and source comparison mock

Date: 2026-10-24.
Status: bounded, inspectable design mock. Production integration, layout adoption and unfamiliar-reviewer understanding are unverified. The [owning packet](../plans/720p/slices/05-explanation-exploration/reviews/pr-file-tree-mockup-v1.md) retains superseded iterations and exact evidence.

## Current experience

Open a full-window, dark editor canvas containing the entire pinned PR’s changed-file tree. Directory branches and compact outlined file objects show one basename plus a small Git change mark: green + added, warm ~ modified, red − deleted when present. Full-path/kind identities keep duplicate names distinct. Containment edges mean contains. Initial framing preserves legible names; the complete tree can extend beyond the screen and remain reachable by pan/zoom. Overview returns a readable PR-root frame rather than shrinking everything into a miniature. The original October23 dark/Inter/quiet-chrome foundation remains the visual reference; giant explanation cards and subsystem tabs are outside this mock.

A file is a spatial **group**, not a flat diff card. Clicking or keyboard-activating its filename expands/collapses its nested contents in the existing PR canvas without moving the camera. Surrounding files and directories remain. Semantic zoom toward a nearby file discloses the same group; zooming out collapses it. One file’s detail is open at a time. Local space reservation moves downstream objects continuously; stable header connectors and full-path IDs remain attached. A group near the screen edge may require ordinary graph pan to read all of its contents. Expansion does not disguise a camera refit as a reading action.

The inner graph has explicit file, native Git hunk, Before source, After source and paired comparison identities. Source nodes carry the exact side’s commit/hash/range, including honest absence for a newly added file. Visible containment and source-comparison relationships connect these objects. This is a grounded subset of a future semantic graph; it does not invent functions, calls, runtime impact or evidence nodes. Unified and split are presentations of the same ordered native change blocks and source identities. Both sides share one hunk geometry and scroll owner; there are no independent side scrollers or inferred function pairings.

## Reading changes and relationships

Only an expanded file has a left change rail. Each dot targets an exact hunk group: green for pure additions, red for pure removals, yellow for a hunk containing both removed and added rows. This uses hunk rows, independently of the file’s A/M/D status. Dots follow proportional native diff-row extent; they are not a minimap of rendered wrapped pixel heights. Labels name the full path, change kind and both source ranges. Activation smoothly scrolls the file’s own viewport to the target, highlights its group and leaves the PR camera/selection unchanged. Repeated activation retargets the native scroll; manual source scrolling updates the current group. Reduced motion gives an immediate equivalent. Overview has no dot clutter.

Mobile defaults to Unified, keeping actual removed/added rows adjacent. Long exact lines use one horizontal comparison scroller with a visible horizontal affordance and persistent line/change gutters, at12px monospace. Both compared rows move together. A replacement initially focuses near its first differing text offset, obtained from the exact strings’ common prefix; this is not semantic alignment. Full lines remain available by horizontal scroll. A500-character source line is not promised to fit a phone. Desktop defaults to split; rendered source height is measured so code stays within its own hunk, with no text bleeding over subsequent groups. Native text selection and inner scrolling own their input and do not pan the outer graph.

Selecting a changed file overlays only that file’s source-observed static import dependencies. Repository targets are resolved against each exact source-side Git tree. One-hop unchanged targets can appear as compact gray context filenames, distinct from changed-file membership. Static built-in/package imports become typed external module identities, with no invented repository target/hash or package resolution. Green/red/gray edges mean added/removed/retained target membership across the two sides, not unchanged bindings or proven runtime behavior. Type imports are included. Unresolved relative targets remain unresolved records, never fabricated files. Non-code/unprepared scope says imports unavailable. Clearing selection removes only temporary context and links.

Activating an import or internal source-comparison **edge** opens an explanation reader: bottom slide-up on mobile, right slide-in on desktop. It identifies the precise from/to relation or hunk/source side, highlights the relevant edge and incident source objects, and separates What, How and Why. Exact pinned citations are inspectable. Prepared source facts, inferred rationale and unknown intent remain explicit; static imports are not calls or runtime impact. Closing preserves the graph camera, file/hunk reading and mode. Explanation prose belongs in this reader, not stuffed into the file node. This reader is neither a question composer nor a live analysis result.

## Fullscreen and controls

The separate quiet top-right fullscreen action changes the **entire main workspace root** to the selected file group. Only that group’s nested source identities and internal relations are rendered. Other PR files, directories, temporary external/context objects and cross-boundary edges are excluded from the rendered graph, not covered by a transparent large card. The same child identities remain. Exit or Escape restores the retained PR camera, selection, expanded state and source reading/mode. Opening from compact state returns to compact state. Escape closes an explanation reader before exiting a file workspace.

A compact segmented icon toggle switches Unified/Split, with accessible names, pressed state and tooltips. It is fixed above the mobile safe area and floating/draggable on desktop. It has no visible mode-word wall. The mobile explanation reader sits above this bar and retains a visible close action. Minimal exit/Overview controls remain; no story/player, subsystem navigation, participant attachment, comment delivery or command execution is introduced.

## Motion and verified limits

Spatial consistency is the purpose of expansion, displaced-neighbor, fullscreen and reader motion. Geometry uses a proposed240ms transition; native smooth scrolling owns dot travel and its browser-selected duration. Same-scale explicit camera transitions use linear interpolation and explicit operation ownership so an artificial temporary zoom-out cannot trigger semantic collapse. Same-zoom movement leaves the detail reducer unchanged. Source reflow during one-node resizing is a deliberate bounded layout cost; it is not a claim of compositor-only performance. Reduced motion removes spatial travel. These thresholds, geometry and timings are mock proposals, not adopted production tokens or changed story semantics.

Author Chrome journeys and sampled intermediate geometry/scroll positions establish bounded engineering behavior. Static screenshots show settled reading states, not smoothness by themselves. Physical touch/trackpad/device performance, native hosts and unfamiliar-reviewer comprehension remain unverified. The independent UI-browser policy gate remains denied/unrun, without retry or alternate access. Prepared explanations have no backend persistence, participant or network effects. Import edge crossings, dense proportional dot touch spacing, long horizontal source reading and fixture-rich bundle cost remain limits for inspection. Prior flat/presentation-led previews are preserved historical artifacts and do not establish acceptance of this nested-group design. Root owns independent review and user feedback; no production publication or adoption is implied.
