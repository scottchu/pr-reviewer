# Bounded TypeScript/TSX source neighborhoods

**Direction:** Accepted slice 04 analysis design

**Contract revision:** `source-neighborhood-v1`

**Implementation:** Pure analyzer/declaration modules and integrated owned-worker/store/React candidate independently reviewed. Actual ownPR understanding and full slice acceptance remain open.

**Parents:** [Architecture](../architecture.md), [source and graph boundary](evolution.md), [reactive ownership](../reactive-design.md)

## User story and meaning

A reviewer selects a changed function and sees its before and after source side by side, its direct callers and callees, and useful unchanged source context. Each relationship opens the call site and declaration supporting it. Unresolved calls and incomplete source scope are visible. The reviewer can retain a source-anchored clarification, return to the selected change, and explain one consequence without treating a static relationship as an observed execution.

Analyze each pinned side independently. A base call targets base source; a head call targets head source. An unchanged file may participate on both sides but retains each side's actual bytes and identity. A paired before/after node is a comparison aid, not a call, proof of semantic equivalence or evidence that the function executed. Source claims, agent interpretation, user correction and actual test results remain separate.

The first supported language surface is `.ts` and `.tsx`. The first useful functions are named function declarations with bodies and immutable named `const` arrow/function-expression bindings, including local/nested declarations. TSX function bodies are parsed as TSX, so ordinary direct calls inside React code are analyzed. The product is React-specific; this subsystem does not promise a reusable cross-framework SDK or complete runtime call graph.

## Pure preparation boundary

The analysis core accepts immutable values and returns immutable facts. It does not open Git, a filesystem, a network connection, SQLite, a host session or a browser, and does not invoke target code or configuration. Parser/checker objects are private implementation details, never stored as domain state or exposed in its public result. A declared in-memory compiler host reads only a normalized source map supplied in this request; all filesystem-like compiler callbacks resolve against that map or return absent. No fallback to the compiler's default system host, current checkout, node_modules, ambient `@types`, downloaded libraries, config `extends`, plugins or package scripts is allowed.

The public preparation operation is `analyzeNeighborhood(input) -> AnalysisResult`, exported through `src/source-analysis/public.ts`; this is a value contract, not an existing gateway/MCP/job API. The implemented integration maps persisted source and queries to it through public ports; exact normalized members and vectors are defined in [semantic protocol values](semantic-data.md). A successful pure result is analysis of supplied bytes only; provenance that those bytes came from the pinned Git objects is established by the acquisition/admission adapter, not invented by the core.

### Input knowledge

| Value | Meaning and validation |
|---|---|
| Request identity | contract revision, snapshotId, repository/provider change identity, immutable base/head commit identities. No actor/session credentials. |
| Source corpus | For each side, normalized repository-relative path, exact UTF-8 content, SHA-256 content hash, object ID when acquired from Git, and status changed/context/declaration-only. Validate hashes, unique side/path, bounded bytes and path safety. The corpus includes unchanged context; a changed-file-only manifest is incomplete for caller discovery. |
| Corpus account | Included paths and excluded/missing/unsupported path dispositions, side commit, acquisition method and whether the supplied inventory covers only changed files, a selected context set or a verified repository enumeration. The core validates consistency but cannot prove a caller's inventory assertion. Output repeats this account. No global completeness inference follows from an omitted exclusion list. |
| Seeds | One or more exact declaration anchors on a stated side/source hash. A seed denotes one supported function body/binding; an ambiguous, absent, out-of-range or unsupported declaration produces a typed unresolved seed, never a guessed function by name. The integration layer selects seeds from actual changed ranges and records that selection. |
| Resolution profile | Fixed `repository-static-v1` profile, with optional normalized, pinned path-alias mappings and their configuration source hash/anchor. Unprovided configuration is explicit, not guessed from the agent's workspace. |
| Budgets | Explicit limits no higher than the defaults below; values and profile are part of analysis identity. |

Input `snapshotId` remains the review's source identity. Additional unchanged context is content-addressed by a separate corpus digest including side/path/hash, excluded dispositions and resolution profile. It cannot silently replace reviewed content. Require the same side/commit as the selected snapshot. The adapter must acquire and retain the exact context bytes so later source links remain available; returning an external mutable path is insufficient.

### Output knowledge

| Value | Meaning |
|---|---|
| Result status | `analyzed` or `unavailable`; analyzed may have unresolved sites/seeds and incomplete scope. Unavailable carries typed identity/input/budget/parser reasons and no success graph. |
| Analysis identity | Deterministic digest of contract, analyzer/parser exact version, snapshot and corpus identity, normalized options, seeds and budgets. Reordering source inputs does not change facts/identity. Changing bytes, config, parser or side must change identity. |
| Function nodes and caller contexts | Named functions have stable ID derived from snapshot/side/path/hash/declaration start/end; display name, supported declaration kind, body/declaration anchors and changed/context status. Names alone are not identities. Calls in a top-level initializer or anonymous callback use an explicitly labeled source-scoped module/callback context node, not a fabricated named function; those contexts are not selectable supported seeds in v1. |
| Resolved calls | Caller node, callee node, one or more exact call-site anchors, target declaration anchor, resolution chain through import/re-export when applicable, method `ts-static-binding-v1`, certainty `resolved_static`. This means the static expression binds to the declared implementation under this profile; it is not runtime dispatch or execution proof. |
| Unresolved sites | Exact site and containing function/module context, syntactic kind, reason and optional candidate declaration anchors labeled candidates. Reasons include unsupported syntax/dispatch, mutable binding, missing/external module, alias/config gap, declaration-only target, ambiguous implementation, parse/semantic obstruction and excluded source. No speculative candidate becomes a call edge. |
| Neighborhood | For each seed, incoming and outgoing resolved direct call edges, unresolved sites inside its body and caller-scope limitations. Only one hop is displayed; the index may inspect all supplied files to locate incoming calls. Neighbors are not recursively expanded by this request. |
| Per-source coverage | Every known side/path records its inventory role, whether selected for analysis, whether exact source was prepared, parse/scan status, invocation sites examined/resolved/unresolved, and explicit exclusion/budget reason. Complete changed-path inventory, selected analysis input, prepared/context coverage and analyzed facts are distinct values. Unknown omitted counts stay unknown; never derive zero from absence. |
| Scope/leaf assessment | Outgoing call-site assessment, incoming search scope, exclusions and diagnostics; use the exact qualified wording below. |

Anchors retain snapshotId, side, path and content hash, one-based inclusive start/end lines, plus zero-based UTF-16 start offset and exclusive end offset. UTF-16 is the parser's coordinate system; never confuse it with byte offsets. Line ranges are derived from exact retained text with CRLF/Unicode cases covered. The existing product's line-only anchors remain usable for UI selection; offsets/hashes strengthen analysis evidence rather than replace immutable source identity.

Sort all nodes, edges, sites and diagnostics deterministically by side/path/source offset/kind. Deduplicate repeated analysis facts by stable identity; retain each distinct call site even when multiple sites connect the same pair. One caller/callee edge may aggregate those sites without hiding them. Recursive calls remain a self-edge. Cross-side comparison must remain a separate relation kind.

### Exact fact identity and ordering

Use the raw lexical canonical JSON recipe in [semantic persistence](semantic-storage.md), SHA256 over UTF-8 and the complete exact anchor fields. A function/module/callback node ID hashes the ordered array of snapshotId, declaration anchor and node kind. A resolved edge ID hashes the ordered pair of caller and callee node IDs. An unresolved-site ID hashes caller node ID, exact site anchor and typed unresolved reason. Display names, actor, locator and body excerpt are not extra ID inputs; the declaration anchor already contains snapshotId, side, path, contentHash, UTF-16 start/end and start/end lines. This exact recipe also gives declaration inventory members their existing node IDs.

Sort source/declaration anchors by raw lexical side:path, then start and end. Nodes additionally sort by kind. Resolved edges sort by caller declaration anchor then target declaration anchor; their distinct call sites retain traversal/source order. Unresolved sites sort by anchor then syntax kind; candidate/signature anchor lists sort by anchor. Neighborhoods follow normalized seed order and refer to these exact IDs. Cross-side comparison remains outside this identity/edge model.

### Preparation public values and coverage interpretation

The request supplies repository/provider/change identity, both immutable side commits, an account for each side, source entries, at least one seed, the fixed resolution profile and all explicit budget values. `DEFAULT_BUDGETS` exposes the accepted maximum values for callers to copy or lower. Inventory and prepared-source budgets are separate: every known path retains a ledger row, while only entries carrying source text count as prepared sources, including unselected prepared entries. Content-less excluded/missing/unsupported rows never consume the prepared-source count. Duplicate requested seeds are deduplicated for facts and identity, but every supplied seed counts against the request-size limit. A missing seed list is invalid input; a supplied seed that fails to identify a body has its own unresolved result while independent source facts may remain available.

Each source entry carries its side/path/commit, inventory role (`changed`, `context`, `declaration-only`), explicit selection flag and optional retained content/hash/object ID. Its optional exclusion is `excluded`, `missing` or `unsupported`. Selection alone proves neither prepared bytes nor analyzed facts. A prepared but unselected file is retained and hash-checked without being supplied to the compiler. Each side's account records `changed-only`, `selected-context` or `repository-enumeration` scope and acquisition method. These are explicit adapter assertions; the analyzer cannot verify that all actual repository paths were listed.

The result carries exact analyzer/parser versions, snapshot/corpus/analysis identities, the repeated corpus accounts, per-source coverage, sorted diagnostics and observed byte/AST/site counts. An analyzed result adds the bounded fact index and one-hop neighborhoods. The index contains facts from all selected supplied source so incoming discovery can find unchanged callers; selecting a seed never creates a transitive edge. An unavailable result omits nodes, edges, unresolved-site facts and neighborhoods entirely. It retains the ledger and observed counts, a typed identity/input/budget/parser reason, the actual budget name and triggering side/path when identified. No partial graph is consumable as success.

Coverage separates `prepared` from `selected`, `parseStatus` from scan `status`, and observed counts from unknown counts. Parse status is `not_parsed`, `parsed` or `failed`. Scan status distinguishes `not_selected`, `excluded`, `missing`, `unsupported`, `pending`, `parse_failed`, `scanned` and `budget_exceeded`. A compiler program can parse a file before the bounded AST walk visits it: `parseStatus: parsed` with `status: pending` explicitly means scan pending, not analyzed. On budget failure, pending rows retain the bound that prevented scanning. `examined`, `resolved` and `unresolved` are null until observed; a complete scan may report actual zero counts. A syntax-failed source has no function/leaf/call facts. An AST/site failure may retain an examined prefix count without resolved/unresolved totals.

Supported declaration seeds match the exact function-declaration span or const variable-declaration span, excluding its containing variable statement and trailing semicolon. Names and overlapping ranges never substitute for an exact seed. `source_unavailable`, `hash_mismatch`, `invalid_range` and `unsupported_or_absent` distinguish seed failures. Module and callback contexts are indexed for evidence but cannot be selected as supported declaration seeds. Header initializers and computed member names are attributed to their enclosing source/body context, not the function body being declared; a leaf statement applies only to the actual body anchor.

Resolved edges aggregate each distinct invocation anchor for a caller/callee pair. Each site carries its ordered import/re-export linkage anchors and overload declaration-signature context. The target is always the unique implementation body declaration, never a signature. Local named exports and identifier default exports retain their linkage too. Type-only imports/exports do not establish executable calls. The `conditional` site flag records optional-call/member syntax; false does not mean the call always runs. All calls retain the separate `resolved_static` certainty and static method label.

Results are deeply frozen value objects, and caller inputs are neither changed nor frozen. A body with actual invocation sites remains `invocations_present` even if none resolve; JSX without explicit calls, rejected configuration or an unresolved seed yields `not_fully_analyzed`. The exact qualified leaf and supplied-files caller wording remains mandatory. A test-related limitation explicitly prevents treating path classification or a source call as execution evidence; no test relevance ranking or test-run receipt is produced.

## Bounded declaration inventory

`listNeighborhoodDeclarations` is the separate pure selection port. `DeclarationInventoryInput` is `AnalysisInput` without `seeds`; callers supply the same contract, immutable identities, corpus, sources, fixed profile and complete lowerable budgets. It never calls the analyzer with a sentinel seed. It shares preflight validation, the supplied-text virtual compiler host and supported AST declaration scan, without resolving invocation bindings or expanding the resolution profile.

The deeply frozen result has `inventory: source-declarations-v1.0.0`, exact `parser`, snapshot/corpus/inventory digests, repeated corpus accounts, complete coverage, sorted diagnostics and observed source/metadata/AST/invocation/declaration counts. `available` adds sorted `declarations`; `unavailable` retains the analyzer's typed reason/detail/limit/triggering source and omits declarations entirely. Syntax-failed files contribute diagnostics and failed coverage, with no declarations; independent valid files may remain available. Missing/unselected/unsupported/excluded sources yield coverage, never guessed choices. An available empty index is valid and does not prove the repository has no functions.

Selectable values carry the existing function node ID, name, kind (`function`, `const-arrow`, `const-function`), exact declaration/body anchors and source role. Named nested implementations and TSX bodies are included. Anonymous callbacks/default functions, module contexts, methods, mutable variable declarations, signatures without bodies, declaration files and declaration-only source roles are excluded. Function declarations use their exact AST span (including modifiers); const bindings use the variable-declaration span, excluding `const`, sibling bindings and trailing semicolon. Source order is side/path, then declaration offset/end/kind. Names, overlapping ranges and cross-side similarity never establish selection identity. Exact returned declaration anchors map directly to analyzer seeds.

`inventoryId` is SHA-256 of canonical JSON containing inventory version, exact parser version, contract/snapshot/change/commit/corpus identity, sorted complete source metadata (hash/object IDs, no text), profile and all budgets. Object keys sort recursively; source rows sort by side/path. Corpus digest and declaration node IDs retain the existing analyzer meanings. No actor/locator/seeds enter inventory identity. Changing identity, source hash/disposition/profile/budgets changes it; input order does not. Existing `source-neighborhood-v1.0.1` analysis identity and facts remain unchanged.

All existing preflight/source/metadata/AST and invocation-scan bounds apply. `outputNodes` additionally bounds the number of selectable declarations (default 2,000), excluding module/callback contexts. `observed.declarations` counts discovered selectable declarations; the 2,001st (or first above a lowered bound) causes whole-index `budget_exceeded` with no declarations and an exact triggering source. This inventory-specific interpretation does not change analyzer node limits or its version. Coverage `examined` counts scanned invocation syntax; `resolved`/`unresolved` remain null because inventory does no call binding. Parsed, scanned, selected and prepared retain their separate meanings. The operation has deterministic work budgets, not a process wall-clock/RSS guarantee.

Amendment implementation `8a2837b` passes 36 focused tests (the 26 existing tests plus ten inventory cases) and strict checks. ## Supported resolution and honest unknowns

| Construct | v1 treatment |
|---|---|
| Direct identifier call to a unique function declaration or immutable const function binding | Resolve lexical symbol and unique implementation; retain source evidence. Check writes/reassignments in the supplied corpus; mutable `let`/`var` and observed reassignment are unresolved. |
| Named/default imported function, renamed import, namespace-import member | Follow the compiler's actual binding through the supplied module graph to one supported implementation. Namespace membership must come from a module import, not a similarly shaped runtime object. Retain import/export source anchors. |
| Explicit local named re-export chain | Resolve a finite chain to one implementation with visited-set/budget protection. Cycles without a unique implementation remain unresolved. `export *` ambiguity/unsupported resolution remains explicit; never first-match by text. |
| Relative modules | Use TypeScript 6.0.3 Bundler resolution over the virtual source map with ESNext modules, no emit, TS extensions allowed and JSX preserved. Accept only supplied local `.ts`/`.tsx` targets reached by that profile. Record the profile rather than claiming it reproduces every target runtime's loader. |
| Path aliases | Support explicitly supplied pinned `paths` mappings relative to one virtual repository root: at most one wildcard per pattern/target, ordered targets, all paths within the corpus root. Use compiler resolution over those inputs. Missing/unsupported config, inherited config, package `imports`/`exports`, external/bare packages and out-of-root mappings remain unresolved; never inspect a user's filesystem to make them work. |
| Overloaded function | A resolved signature alone is insufficient. Link all selected signature evidence to the same symbol's unique supported implementation body. Declaration-only overloads or ambiguous/multiple implementation targets remain unresolved. Do not present a signature as executed code. |
| Nested functions and callbacks | Own call sites belong to the nearest function body, not its outer declaration. Named nested const/function declarations can be nodes. Anonymous callback bodies have a local source-scoped caller context, but passing a callback is not proof the receiving API calls it. A function-valued parameter invocation is unresolved. |
| Optional calls | A uniquely bound direct optional call may be a static edge labeled conditional. This is no claim it runs. Unresolved optional member dispatch stays unknown. |
| Methods, constructors, dynamic/computed properties, mutable aliases, `.call`/`.apply`/`.bind`, returned functions, unions, reflection/eval, dynamic import | Record invocation sites and an unsupported/dynamic reason. Do not use a checker signature or apparent property name to invent a definite implementation edge. Class/prototype dispatch and higher-order flow analysis are outside v1. |
| JSX tags and props | Preserve TSX parsing; tags, props and callback passing do not become call edges. Show an explicit framework-invocation-not-analyzed limitation for JSX-containing bodies. JSX/reference enrichment is later scope, not inferred execution. |
| Test source | If a known test file actually contains a resolved call to the seed, it can be a source-backed caller/context. Test path/name heuristics are labeled classification, not relevance or execution. Assertion text/test presence alone never establishes a pass. |
| Invalid or newer unsupported syntax | Syntactic errors invalidate facts from that file; retain its disposition and unresolved imports/callers. A diagnostic intersecting a call/import/declaration needed for resolution blocks that edge. Unrelated diagnostics are reported without blanket claims that the target program type-checks. No emit/transpile of target code. |

The profile is intentionally narrower than target TypeScript compilation. No default library or ambient packages are loaded. Unknown standard-library/property calls remain visible. Checking lexical bindings under this bounded profile cannot establish runtime reachability, evaluation order, effects, dependency injection behavior or real execution. Business rules for certainty, budgets and accepted facts belong to the source-analysis domain, never to React rendering or stream operators.

### Exact unresolved-site reason vocabulary

An unresolved site's required reason is exactly one of these15 literals. The literal participates in its ID as `[callerNodeId,siteAnchor,reason]`; a display label or conceptual synonym is not a compatible replacement. These site reasons are distinct from whole-request unavailable reasons, loader issues and unresolved-seed codes. Candidates remain source anchors for investigation, never confirmed call targets.

| Literal | Meaning under the bounded static profile |
|---|---|
| `unsupported_dispatch` | The invocation's dispatch form is outside supported direct/namespace-import binding, including runtime object methods, computed properties and constructors. |
| `dynamic_invocation` | Dynamic invocation form such as eval, dynamic import, calling a returned function, tagged template or decorator; no definite supported implementation is asserted. |
| `mutable_binding` | The target binding is mutable or an observed write makes it uncertain, including an affected namespace import/member. |
| `missing_module` | A relative module cannot be resolved from the supplied source map. |
| `external_module` | A bare/package module lies outside the supplied local profile without a supported pinned alias resolution. |
| `alias_configuration_gap` | A package-import/alias-shaped request or blocked pinned configuration cannot be resolved within the supported configuration facts. |
| `declaration_only` | Binding reaches declarations/signatures without a supported implementation body. |
| `ambiguous_implementation` | A unique supported implementation cannot be selected, including competing implementations/declarations or unsupported star-export ambiguity. |
| `parse_obstruction` | Syntax failure in a required target module obstructs binding. |
| `semantic_obstruction` | Required symbol/export semantics or an intersecting compiler diagnostic prevents a supported source binding. |
| `excluded_source` | The requested module is known in the supplied inventory but unavailable to the selected prepared-source resolver. |
| `missing_binding` | The invocation has no lexical symbol or no declarations establishing its binding. |
| `unsupported_binding` | A symbol exists but its declaration/binding form is outside supported callable implementations, including type-only imports/exports and function-valued parameters. |
| `cyclic_resolution` | Alias/re-export traversal revisits a binding without establishing a unique implementation. |
| `reexport_limit` | The finite named re-export traversal would exceed the configured reExportLinks budget. |

Write detection must follow lexical binding identity for ordinary assignments, updates, destructuring and iteration assignment targets. In a destructuring shorthand, the compiler's property symbol and written value binding are distinct; using only the property symbol can falsely confirm a later call to a reassigned function. Inspect the written value binding, and do not mark unrelated right-hand/default-value expressions as binding writes. This rule follows the immutability policy rather than assuming a const keyword proves no observed write. Named function-expression recursion may resolve to its owning supported const implementation; passing that expression as a callback still does not establish an invocation.

TypeScript assertion and non-null wrappers on an assignment target do not make the underlying binding immutable. Observed-write detection must unwrap those transparent target expressions. A computed namespace-import member write must also prevent a later member call from being confirmed against an earlier implementation; this is conservative source uncertainty, not evidence that the target runtime permits mutation of module exports. Runtime object member writes must not be promoted into namespace bindings or method-call edges. Independent review found these missing cases in the initial preparation candidate; correction and revalidation are recorded in the preparation evidence.

For a namespace write with a literal member name, mark that actual exported symbol uncertain. For an unknown computed name, retain uncertainty for the namespace and its exported symbols; do not select a replacement target or infer its runtime effects. Determine namespace membership from the unwrapped lexical import binding, so assertions cannot hide the write and similarly named local objects/parameters cannot become module namespaces. Assertion, type-assertion, non-null and satisfies wrappers are transparent only for this observed-write classification; their presence does not broaden supported call-expression dispatch.

### Leaf and caller-scope statements

A confirmed outgoing leaf means only **“No explicit invocation sites in this function body under the supported syntax scan.”** It is allowed only for a successfully parsed supported body, fully scanned within budget, with no call/new/tagged-template/dynamic/JSX/other unmodeled invocation constructs or unresolved sites. Nested function bodies are assessed separately. It never means no effects, no property getters, no indirect framework behavior or no runtime dependency.

If invocations exist but none resolve, show unresolved calls; never a leaf. If scan/source/budget/config is incomplete, show not fully analyzed. For incoming calls, zero matches is **“No resolved callers found in these supplied files”**, always with corpus coverage. Never assert no callers in the repository or no external consumers, even when the provided inventory was a complete enumeration; dynamic/unsupported calling forms remain outside proof.

## Budgets and lifecycle

Defaults: 4,096 known inventory paths per side (`inventoryPathsPerSide`); 2 MiB combined ledger metadata (`inventoryBytes`); 128 prepared source entries per side (`filesPerSide`); 256 KiB UTF-8 per prepared file; 4 MiB combined prepared source; 64 seeds; 200,000 visited AST nodes combined; 10,000 invocation sites; 2,000 returned nodes and 4,000 returned distinct call sites; alias map at most 32 patterns with four targets each; re-export traversal at most 32 links per resolution. Inputs may lower but not silently raise these limits. Every prepared entry counts even when unselected; every content-less inventory row counts only toward inventory bounds. Both sets of limits are explicit request values and participate in canonical analysis identity.

The combined ledger metadata size is the UTF-8 byte length of the canonical JSON array of all source-entry metadata, in side/path order. Retain each entry's side/path/commit/role/selection/exclusion and its source hash/object ID; remove the content text and represent absent source as `source: null`. Canonical JSON sorts object keys; array delimiters, commas, field names and escaped strings count toward the byte limit. This measure excludes the text itself, corpus-account/profile/seed values and compiler objects. Prepared source has its separate file/combined byte limits. Exceeding either inventory bound rejects before compiler creation and returns every known coverage row with unknown unparsed counts rather than silently dropping exclusions. The observed metadata byte count is reported independently from prepared text bytes.

Returned-site limits count both resolved and unresolved invocation sites; unresolved calls cannot evade the output bound. Source size is UTF-8 bytes, while anchors remain UTF-16 offsets. Valid BOM, CRLF and astral Unicode text retain their exact identity and coordinate system; malformed string encodings reject before parsing. Finite named re-export traversal reports a site-level `reexport_limit` or `cyclic_resolution`, retaining no speculative edge.

Preflight oversized/invalid input rejects before parser construction. Exceeding an AST/site/output global budget returns `unavailable: budget_exceeded` with the actual bound and no partially successful neighborhood; users must narrow scope explicitly. Retain the per-side/path input disposition ledger and exact observed counts, marking unvisited files as not analyzed and reporting the triggering file/limit when known. Do not invent an omitted-site count for an unscanned file. A generic global warning is insufficient: consumers must distinguish prepared files from selected or actually scanned files. Do not return a graph that silently omits inconvenient edges. Cyclic resolution terminates by visited identity and reports its reason. Invalid content hashes/identity reject the whole request before facts are emitted.

The pure synchronous core has deterministic work bounds, not a hard wall-clock interruption guarantee while the compiler parses/checks. The implemented execution adapter runs it outside gateway transactions/UI threads in an owned worker/process with a20-second deadline and explicit timeout/unknown result semantics. Actual process faults and lowered deadlines are tested; its256MiB setting limits V8 old space, not RSS. No unmeasured full-input latency/RSS guarantee follows. Cancellation, superseded snapshot and late-result fencing belong at that boundary; they do not mutate core inputs.

## Integration and graph clarification

The provider import result includes changed-file source, dispositions and hunks; it remains separate from the implemented unchanged-caller corpus. The source adapter reads additional bounded immutable context from the same base/head objects through its explicit public acquisition port, retains its bytes/hashes, and reports omitted scope. No source-analysis module may reach into acquisition internals or read the live checkout as a shortcut. Context loading, analysis scheduling and result admission occur outside short dispatcher transactions; authorized domain commands admit results for their exact snapshot/corpus/analysis identity. Managed routes expose committed results, ownership, teardown and diagnostics.

Present confirmed static calls separately from existing comparison/contains/document-reference edges and unresolved candidate sites. Before/after placement, changed/context labels, scope limits and evidence access are visible without relying only on color. A reviewer can follow one incoming/outgoing edge, open both evidence anchors, inspect an unchanged neighbor, annotate that source and return. Keep the complete bounded fact/coverage index accessible, but initially display one selected function and its before/after pair plus a readable subset of immediate neighbors (at most 12 nodes). Explicit remaining counts and accessible neighbor lists support further expansion without fitting all facts into one unreadable canvas. A display limit changes neither analysis coverage nor leaf status. Graph focus/expansion must not retarget the current source selection, question anchor or draft; require an explicit source-opening action. Private expansion/viewport/selection does not create shared writes.

Graph clarifications are persisted user/agent annotations with immutable source anchor, actor, text, evidence kind and expected graph revision. Add/update uses the normal authorized durable command/receipt boundary and atomic graph CAS. Unrelated comment revisions do not reject a graph update. Reject stale graph revision or stale/revoked generation with no partial mutation; wrong-snapshot anchors reject. Preserve prior author/correction provenance. Ordinary graph writes do not wake the agent. The implemented PutGraphClarification command, receipt/CAS ports and physical layouts are specified in [semantic persistence](semantic-storage.md).

## Parser decision and rationale

**Selected analysis dependency:** runtime alias `typescript-analysis` pinned to `npm:typescript@6.0.3`; the existing `typescript@7.0.2` compiler/check toolchain remains unchanged. Root explicitly serializes any later package/lockfile write; no install belongs to planning.

Local inspection of the installed 7.0.2 manifest found the top-level version export and `unstable/*` APIs, rather than the classic API assumed by many examples. Microsoft's [compiler API guide](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API) explicitly applies to 6.0 and earlier, and the [6.0.3 release](https://github.com/microsoft/TypeScript/releases/tag/v6.0.3) is stable. Select that pinned API for parser, in-memory Program/CompilerHost and binding/signature inspection. Relevant public types are in the [versioned compiler definitions](https://github.com/microsoft/TypeScript/blob/v6.0.3/src/compiler/types.ts). The [module reference](https://www.typescriptlang.org/docs/handbook/modules/reference.html) describes resolution distinctions; the profile records them rather than treating aliases as runtime rewriting. These references support the API choice; actual preparation results are recorded separately below.

A handwritten regex/name matcher was rejected because it cannot preserve lexical shadowing/import identity. AST-only syntax would locate calls but cannot substantiate cross-file symbol bindings. Full program/call-flow/framework analysis is disproportionate and would encourage false precision. The 7.x unstable/beta API would add API/native-process uncertainty to a bounded pure preparation chunk; using an explicit 6.0.3 alias avoids replacing the existing compiler. This costs a second pinned package and requires honest rejection of unsupported newer syntax. Reassess after evidence rather than silently broadening language support.
