# Semantic persistence and recovery

**Contract:** `semantic-graph-v1` / `analysis-worker-v1`

**Date:** 2026-10-24 UTC

**Status:** Slice04 integration in progress; independently reviewed worker, React journey and whole-product acceptance remain open.

**Parents:** [Semantic meaning and execution](semantic-graph.md), [existing persistence compatibility](persistence-compatibility.md).

## Identity and physical representation

The existing single SQLite connection owns semantic writes alongside existing review/import records. Source/history tables and snapshot IDs remain unchanged. `analysis_jobs` stores one JSON job body keyed by jobId; `analysis_graphs` stores one JSON graph control body keyed by reviewId/snapshotId. `analysis_records` stores canonical immutable bodies keyed by reviewId/kind/id, with snapshotId and encoded byte count. Kinds are corpus, inventory and analysis. `analysis_receipts` stores commandId, actorId, payload fingerprint and JSON receipt. `graph_clarifications` stores clarificationId, reviewId, snapshotId and JSON author/revision history. `analysis_owner` stores the current opaque runner generation. These additions neither rewrite old review bodies nor infer source-project metadata for legacy snapshots.

The graph control body has analysis generation, graph revision and selected analysis ID (initially0/0/null). Generation increments for a new request; graph revision increments once for admitted facts or a clarification. Job revision advances for each committed job/process transition. Existing question/reply review revision is independent. A compute admission writes its result, selected pointer, graph revision, job terminal state and `analysis-admit:<jobId>` receipt in one transaction; unavailable compute results are retained outcomes without replacing the last graph. Receipt fields are commandId, actorId, applied/rejected state, reviewId, snapshotId, analysisGeneration, graphRevision, optional jobId/jobRevision, result and optional error.

A corpus immutable body contains the complete original loader corpus plus its issues. Inventory and analysis bodies are the complete exact verified pure-module results. Identity and canonical body equality must both agree on repeat admission; a same-ID/different-body or different-snapshot record conflicts. The quota is the sum of UTF-8 bytes of canonical bodies of distinct immutable records for the review, including source text/escaping/provenance/coverage/facts; job and generation references do not recharge the body. Exactly64MiB is admitted and one byte over rejects atomically. Lower test quotas never enlarge the production ceiling. The quota does not measure all SQLite bytes, receipts, job journals or clarification text.

Semantic canonical JSON recursively orders object keys by raw lexical UTF-16 ordering, preserves array order and uses JSON string/number encoding. SHA256 hashes its UTF-8 encoding. This is deliberately separate from the retained legacy domain canonical implementation. The corpusId uses the loader's original ordered JSON recipe: its complete corpus data excluding corpusId, with each source's content omitted but source hash/provenance retained. Protocol inputFingerprint hashes the complete canonical worker input. None of these identities contains a worktree locator, credential, actor or process ID.

For exact pure-module identities, sort source rows by raw lexical `side:path`. For each source metadata row preserve side/path/commit/role/selected/exclusion; its `source` becomes contentHash plus optional objectId, or null when no prepared bytes exist. corpusDigest hashes canonical `{sources: sourceMetadata, corpus: sideAccounts, profile}`. The analysisId hashes contract, analyzer `source-neighborhood-v1.0.1`, parser `typescript@6.0.3`, snapshotId, change identity, commits, corpusDigest, profile, normalized seeds and budgets. Seeds deduplicate exact side/path/hash/start/end and sort by side:path, start, end and hash. The inventoryId hashes inventory `source-declarations-v1.0.0`, parser, contract, snapshotId, change, commits, side corpus accounts, sourceMetadata, profile and budgets. A schema/version/source/hash/coordinate disagreement cannot be cured by accepting the child's claimed digest.

## Public commands and views

All command objects are strict. RequestAnalysis accepts commandId/reviewId/snapshotId/expectedAnalysisGeneration, optional explicit priorityPaths by side (at most64 total), owner worktree locator and optional manual sourceProject. If omitted, the locator may come only from an already admitted matching import's pinned candidate; absence returns source_locator_required. Manual snapshots require an explicit sourceProject or source_project_required. Provider snapshots use retained candidate identity. Neither flow rediscoveries provider heads. Agents cannot request context or change locators.

SelectAnalysisDeclarations accepts commandId/jobId/expectedJobRevision/corpusId/inventoryId and one or two exact inventory declaration IDs, at most one per side. Arbitrary source, seeds and implicit name/path pairing are rejected. CancelAnalysis accepts commandId/jobId/expectedJobRevision. Queued cancellation prevents a claim; active cancellation records intent until termination is confirmed. Stale generation/job CAS returns analysis_generation_conflict/analysis_job_conflict. Exact authorized receipt retries return the original receipt; changed payload/actor yields command_conflict. Authorization is checked before receipt replay, including attached agent generation/revocation.

Analysis queries accept reviewId/snapshotId, optional explicit historical analysisId and independent minimumGraphRevision/minimumJobRevision. An unmet minimum returns revision_unavailable. The view contains requested generation, graph revision, currentSnapshotId, selectedAnalysisId and public job status/journals. `preparation` identifies the newest requested generation's job, corpus account, inventory and optional unavailable/admitted result. Top-level analysis/corpus/inventory describe the selected admitted result (or current initial preparation when no result exists). This separation preserves prior facts while a new inventory is awaiting choice or an analysis fails. No query can retarget the selected source snapshot. Explicit historical analysis selects only admitted historical facts. Polling returns corpus metadata/accounts/complete ledger/issues and source metadata; source text uses the exact source query and is not repeated across all history.

A context source query must exactly match reviewId/snapshotId/corpusId/side/path/contentHash. It returns retained content, objectId, commit, role and source identity after authorization, without reading Git or local files. Removing the checkout cannot invalidate admitted evidence. Jobs omit credentialReference, actor-owned locator/sourceProject and private priority inputs from public projection. Diagnostic paths never include credentials or source text.

PutGraphClarification accepts commandId/reviewId/snapshotId/selected analysisId/expectedGraphRevision, text1–4000, kind interpretation/question/correction, one primary exact analysis anchor, at most8 same-analysis evidence anchors, and optional existing clarificationId/supersedes. The server issues new clarification IDs. Source anchors include contentHash, UTF-16 start/end offsets and exact start/end lines; end is exclusive and endLine contains max(start,end-1). Updating keeps primary/source/analysis/supersedes immutable and appends an author/time/revision record. An agent edits only its own explanation; the user may append a correction to any. A new anchor requires a new explanation with supersedes provenance. Stale graph revision or another selected analysis yields graph_conflict. Facts and unresolved certainty cannot be replaced through this command. No inbox item or wake occurs.

## Owner, phase and lease formats

Owner-only jobs retain credential reference (SHA256 of the bearer, never the bearer), actorId, worktree/sourceProject, priorities, generation, jobRevision, source/result IDs, selected declaration IDs, context issues/failure account, process invocations and optional admission receipt. At most8 pending jobs/choices are eligible. New requests supersede pending same-snapshot generations while preserving old admitted evidence; an old unknown effect remains unknown and blocks execution even after supersession.

Each invocation has fresh invocationId, app ownerRunId, phase context/inventory/compute, running/completed/cancelled/unknown state and ordered process observations. Context journals only Git, inventory/compute only Node. Requested is committed before spawn, started includes PID and verified process start identity when available, exited includes exit code/signal/reason. Ordinals are contiguous; another process cannot begin while a prior observation is not exited. Context permits at most2048 launches and workers exactly one per invocation. Grant authority is a live WeakMap record bound to owner/job/invocation; serialized objects and import grants cannot substitute it.

The shared execution_owner row contains the owner epoch; execution_lease contains kind import/analysis, jobId, invocationId and phase. Store initialization establishes the epoch once before runners begin; their individual beginOwner operations never reset the other subsystem. Claims acquire the slot atomically. Matching definitively quiescent completion releases it. An old store epoch, wrong grant, wrong phase or wrong release rejects. Legacy import/semantic running or unknown records block acquisition even if the lease row is absent; startup reconstructs its occupancy. Comments and graph writes do not wait for the effect slot.

Lifecycle is context_queued → context_running → inventory_queued → inventory_running → awaiting_declarations → compute_queued → compute_running → admitted, with unavailable/failed/cancel_requested/cancelled/superseded/unknown distinctions. Each boundary commits before its next effect. Context required-source failure retains its exact complete loader failure account when available. A phase_limit before a loader return has no invented ledger or complete/zero unvisited count. No partial graph is admitted. Worker result/schema/version/source checks run outside transactions; short owner transactions recheck current authorization/generation/cancellation and immutable identity.

On restart, queued unclaimed work may run once; an already retained corpus/inventory with no next claim may continue the next phase. Claimed unfinished invocations become unknown and never replay. A requested-but-not-observed process cannot be presumed absent; no reused/unverified PID is killed. Only verified absent owned groups/definitive process observations permit quiescence reconciliation, which marks the interrupted job failed rather than retrying it. An explicit new request after quiescence starts a new generation. Already admitted records/receipts query without a Git/compiler launch. App shutdown signals both runners before awaiting them; unresolved process ownership remains durable and retains the slot.

## Validation limits

This document records the derived integration contract, not completed acceptance. Real process fault evidence, atomic quota boundaries, full history/clarification CAS races, actual React usability, graph-first comprehension and fresh whole-product docs-only audit remain independently required by slice04. Native/Claude/human limitations from the accepted predecessor remain open.

Parent verification and projection are bounded work too. Index supplied sources and line starts once, then look up exact source/UTF-16 spans without rescanning source text for every repeated anchor. Validate bounded node/site/reference/coverage conservation and semantic labels as well as JSON shape/digests: genuine edges cannot coexist with a no-callers/leaf claim, and missing required limitations or impossible counts are rejected. The worker deadline does not excuse unbounded gateway-side validation. Source-preparation joins and overlap checks index unique side/path while preserving every retained manifest occurrence and complete loader ledger.

Public command IDs reserve the `analysis-admit:` prefix for owner-issued admission receipts; a caller cannot preoccupy a future job's receipt ID. Clarification coordinates use the parser's line semantics: CRLF is one break (the LF offset remains on the previous line), standalone CR/LF/U2028/U2029 each start a new line, BOM is an ordinary UTF-16 code unit and astral characters occupy two. They do not reuse the legacy source lineCount's LF-only representation.

The parent rejects declaration/graph nodes whose declaration or body refers to a merely prepared but unselected, excluded, unparsed or unscanned source. Correct hashes and recomputed node IDs alone do not establish scan eligibility. Result coverage conserves observed invocation counts; scanned compute rows reconcile actual unique resolved/unresolved sites and their examined totals. Nonempty incoming/outgoing facts cannot be relabeled as no-callers/leaf; mandatory static-binding-is-not-runtime-execution, test-path-classification-is-not-execution-evidence and applicable incomplete-scope limitations remain present. Canonical body encoding/sizing and witness verification happen before the transaction; admission rechecks authority, generation, cancellation and immutable record conflicts inside it.

Owner-epoch fencing applies before every grant/owner operation and every effect observation, launch-limit lookup and cancellation check, including beginOwner. Advancing the shared store epoch cannot leave an old runner authorized to journal a new requested process while only its later release fails. A fenced old owner cannot clear the retained lease. An omitted locator is resolved only from an import whose state is admitted, whose authoritative admission receipt is applied for this exact review/snapshot, and whose complete retained candidate equals that snapshot's candidate; queued/acquiring/result-ready imports and same-pins/different-candidate metadata are insufficient. Manual snapshots without that retained provider identity still need an explicit locator.

A context witness binds the complete original loader issues as well as the corpus/snapshot/job. Retaining the same incomplete corpus with its actual inventory/tree/required-source warning removed or replaced is a provenance conflict. Source hashes and enumeration flags do not replace those attributed reasons and paths.

## Bounded owner diagnostics

Analysis runner diagnostics retain the integration registry's id/scope/cursor rows. `cursor` counts route publications, including no-op timer/request emissions; it is never a committed database revision. Each live route adds cursorMeaning=route_publications, disposition=active/fenced, a bounded sanitized failure code or null, and at most two job summaries: the latest job and the current running/unknown effect job, deduplicated by jobId. A summary contains reviewId, snapshotId, jobId, invocationId or null, analysisGeneration, committed jobRevision and graphRevision, phase or null, state and sanitized reason. It contains no locator, credential/reference, process arguments or source text.

The private owner diagnostic query checks the shared epoch and runner generation. The runner caches the last successful bounded snapshot; if fenced, diagnostics expose that disposition/failure with the last known revisions and do not attempt further forbidden old-owner reads. Arbitrary error messages become analysis_failed rather than source/path dumps. Disposing removes every route, so diagnostics returns the established empty array; no retained diagnostic row implies an active subscription after shutdown. These are in-process observations, not durable job authority, a new telemetry service or a general scheduler.

A newer request preserves an older unknown invocation's original failure reason and job revision; supersession is not evidence that its uncertainty was resolved. Known pending work may become superseded, while unknown occupancy remains unchanged until a supported quiescence observation. This keeps the original failure disposition available to the bounded diagnostic projection.

Diagnostic sanitation uses an explicit allowlist of stable authority/lifecycle, source-acquisition and fixed worker failure codes, shared by job summaries and runner failures. Identifier-like shape, length or an analysis_worker_ prefix does not establish that an error is an approved code. Unrecognized identifiers (including private source names), paths, tokens, SQL messages and other arbitrary text become analysis_failed. Known stale_execution_owner/stale_analysis_runner codes still produce fenced disposition; known phase/resource/termination codes retain their distinct meanings.
