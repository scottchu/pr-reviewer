# Durable repository-path import jobs

**Contract revision:** `import-job-v1` (bounded launch/quota clarification; existing persisted/source identities unchanged)

**Direction:** Accepted bounded slice 03 design

**Implementation:** The bounded implementation has independent cumulative engineering, actual GitHub own-PR import/continuation/navigation and docs-only knowledge-readiness evidence. Its structural graph remains a source navigator, not a complete semantic explanation. Operational publication/deployment and full-round/native/human gates have separate receipts; do not infer them from implementation status.

**Parents:** [Review/source history](evolution.md), [existing contracts](contracts.md), [reactive ownership](../reactive-design.md)

## User journey

Enter a local repository/worktree path. The app discovers the corresponding PR/MR using existing authenticated provider tooling, presents an explicit choice when needed, shows progress, and opens a complete changed-file/hunk ledger after verified admission. A unique verified candidate can continue automatically because the request is to import that path; incomplete discovery never implies uniqueness. Multiple candidates, unavailable routes, detached/default branches and no match remain explicit. A reviewer can continue discussing an already open review while acquisition runs.

The product flow is path → choice/progress → review. Show concise human states and actionable errors; process journal rows and internal identities belong in diagnostics/evidence, not the primary flow. Imported source is immutable. A new head adds history only after the source and expected-current check pass; it never moves old questions, changes credentials or selects another agent session. The GitHub route uses existing `gh`; absent `glab` is an unavailable GitLab route, not permission to install it or infer GitLab success.

## Simple single-owner design

Use the existing app/SQLite owner and one bounded asynchronous import runner. The runner invokes the acquisition subsystem through its public value/effect ports and starts only fixed `git`, `gh` and `glab` commands with argument arrays. It is not a new service, remote worker, daemon or shell executor. Native async coordination and the managed registry are sufficient; no reactive-library dependency is selected.

SQLite stores job intent, phase/selection, revisions, durable receipts, invocation/process observations and result references. Every mutation uses authenticated domain ingress or a narrowly scoped private internal command grant from the same owner. A transaction ends before subprocess spawn, provider/Git I/O, artifact I/O, source verification or user selection. Waiting jobs do not hold transactions or the runner slot. One active import invocation protects process ownership; discussion and other authorized review commands use independent short transactions and remain usable.

The acquisition module has no database/UI access. Source preparation owns the acquisition-v1 verification/mapping boundary and mints an internal witness only from its trusted public acquisition call, not a caller's JSON or “verified” flag. Domain/storage owns immutable review admission, permissions, CAS and receipts. UI collects intent and renders committed queries; neither components nor stream operators implement job/admission policy.

## Identity and authority

| Identity | Meaning and boundary |
|---|---|
| commandId | One authenticated intent and canonical payload fingerprint. Same actor/payload retries return original receipt; changed payload conflicts. Job commands do not reuse question or admission IDs. |
| jobId | Durable user import request with owner actor and credential reference, canonical requested path, target mode and bounds. It survives browser/process restarts. No bearer token is stored in job data. |
| discoveryRevision | Versioned candidate set and issues. Explicit selection names a candidate from this exact set; stale/foreign selection rejects. |
| jobRevision | Orders job state/readback. It is not a review revision. Job receipts identify job scope and minimum job revision; successful admission additionally returns actual review revision/snapshotId. |
| invocationId | One claimed effect phase (discovery, acquisition or explicitly required re-verification), distinct from commandId/jobId. Persist before any subprocess. Retries of an unknown invocation never get a new ID automatically. |
| ownerRunId / generation | Exact current app owner and runner claim. The exclusive data-root/runtime lock remains required. Restart advances runner generation; prior in-memory grants cannot apply late results. |
| process observation | Invocation plus ordinal, fixed executable role, requested/spawn-observed/exit-observed state, owned PID/start evidence, exit/signal and bounded reason. Do not persist credential-bearing argv, provider stderr or token values. |
| artifactId | Owner-generated identifier bound to job/invocation, content digest/byte length, schema/identity scheme and retained result. It is not an arbitrary filesystem path or permission to open a supplied URL. |
| admissionCommandId | Stable derived identity for this job/result/target admission, retained through crash/readback. Initial create and continuation are explicit distinct modes. New explicit conflict resolution uses a new command, never alters an old payload. |

Only the authenticated local user may request/discover/select/cancel/admit source. Existing agent attachments can read authorized source and reply under their generation; bootstrap and agent credentials cannot import arbitrary filesystem paths or enlarge their review scope. Import grants no new attachment and never forks/resumes a substitute session. Apply-time checks use the request's actual active owner credential reference and current target authorization; recorded actor strings alone do not authorize a late result.

The runner obtains a nonserialized internal grant bound to job, invocation, phase, generation and permitted result transitions. It can report only that invocation's observations/result; it cannot issue general user commands or write another review. External `/api/commands` callers cannot forge this grant. No new worker HTTP endpoint, bearer credential in an artifact or global session setting is needed. Same-OS-owner trust is retained; this is not remote attestation.

## Durable lifecycle

States and observations remain separate: command accepted is not a process start, a successful CLI exit is not a complete acquisition result, and a prepared result is not an admitted snapshot.

| State / transition | Required semantics |
|---|---|
| Request → queued discovery | Atomic job creation and receipt; validate owner/path shape/bounds. Resolve real worktree via the trusted acquisition port, not by changing cwd/branch globally. |
| Claim → discovering | Atomic CAS from eligible queued state, allocate invocation and private grant, persist launch intent; release transaction before effects. Persist each subprocess request before spawning and record observed start/exit independently. |
| Discovery → choice required / unavailable / acquiring | Retain exact candidates/issues/revision. Multiple or incomplete routes require explicit selection. No candidate produces a truthful unavailable/no-match result. A fully unique result pins that candidate before automatic acquisition. |
| Selection → queued acquisition | User command names candidate identity plus discoveryRevision and target choice. Validate membership and authorization; no arbitrary candidate JSON becomes trusted metadata. Import refreshes provider identity and rejects drift as stale rather than importing a different head. |
| Acquisition running → result ready | Trusted source-preparation call invokes reviewed acquisition public port and validates full result/schema/identity; all owned effects have observed completion. Atomically publish a complete owned result artifact, then commit its reference and result receipt. An existing provider result may have unsupported/missing entries; that differs from a failed whole import. |
| Result ready → admitted | After artifact verification and an in-memory witness, use one atomic admission transaction for source/review changes, admission receipt and job disposition. Result references and source remain exact. Emit committed view updates only after commit; no agent wake. |
| Admission conflict | Retain result and typed reason (current snapshot, review identity, source/metadata conflict or limit); no partial history mutation. Offer explicit inspection/target reconciliation. No automatic retarget to the new current snapshot. |
| Definitive unavailable/failed | Record actual reason, phase and whether any process ran. A missing tool before spawn is different from a timeout/unknown launch. An explicit new request may retry after process quiescence; the old job/history remains. |
| Cancel requested | Durable owner command. Before claim/selection it cancels without launch. During an owned invocation stop new subcommands, request termination only of verified owned processes/groups, await evidence and record confirmed cancelled or unknown. |
| Unknown | Startup/crash/uncertain acknowledgement cannot establish whether effects ran or stopped. Retain original invocation/process evidence, quarantine it from replay and reconcile safely. Elapsed timeout or PID absence alone cannot reconstruct a missing result. |

The owner tracks child handles for normal cancellation and records process start identity for recovery. Never kill a reused/unverified PID or a process group belonging to another runtime. Confirm termination using owned process/group observations appropriate to the supported host; signal delivery alone is not cancellation. If termination cannot be established, show unknown and retain evidence. A cancellation/admission race is serialized: if cancel is committed first, no later source admission; if admission committed first, cancel reports already completed and does not delete source/history.

On restart, unclaimed queued work may be claimed once. Claimed work without definitive outcome becomes unknown; do not invoke acquisition/discovery again automatically. A persisted complete result with a matching admission receipt is read back without relaunch. A result-ready artifact lacking an admission receipt is verified before continuation. Because witnesses are in-memory, restart requires a new **explicit** owner re-verification action using a separately journaled invocation against the same pinned candidate and reviewed acquisition algorithm; it cannot replay an unknown original invocation. Provider drift during that re-verification rejects as stale and preserves the old result. No fabricated historical provider response is supplied to make verification pass.

A new job after an unknown one is an explicit user action, never an automatic retry. The owner first establishes that the old invocation is no longer running; otherwise it still occupies the one active effect slot. Existing reviews/comments remain usable. This conservative limitation is acceptable for the first single-host implementation and must be visible in diagnostics and recovery guidance.

## Public operations: existing versus new

Existing 02B ports are `store.command` for review writes, `AddSnapshot` with expectedCurrentSnapshotId, `store.review` with optional historical snapshot selection, user-only review listing, and public `source-preparation` manual verification/witness checks. These ports have bounded independent engineering and actual own-PR continuation/navigation acceptance; full native/human/480p acceptance remains separate. `store.prepare` remains bounded setup/recovery, not authenticated product import ingress.

The candidate implements RequestImport, ChooseImportCandidate, CancelImport, explicit ReverifyImportResult and AdmitImportResult, with the strict owner command shapes below. Authorized job queries return the active credential's jobs and their revisions. These are candidate interfaces, not final slice acceptance. Internal claim/process/discovery/result/admission commands use the same store owner and durable receipt/transaction policy through the private execution grant.

Initial import uses the verified review-creation transition through private job admission, atomically creating review/source/receipt and marking the job admitted. There is no raw provider-manifest HTTP CreateReview command; the owner RequestImport lifecycle and its live verification witness authorize creation. Reserve its generated reviewId once the target choice is fixed. Repeated exact admission returns its receipt; it must not call setup `prepare` from HTTP. Before creating, check stable provider/host/target-project/change identity in the same transaction: if an existing review appeared, return an explicit existing-review conflict/choice instead of silently creating a duplicate or overwriting discussion. Legacy duplicate reviews are preserved and listed for explicit selection; do not migrate/deduplicate them behind the user.

Continuation uses AddSnapshot semantics through the same domain transition and witness boundary, extended to `acquisition_v1`. Pin reviewId and expectedCurrentSnapshotId before acquisition. Preserve exact retained-snapshot idempotency without rewind, source conflict rejection, membership checks and old question/reply/source queries. If current changed, retain the result and require an explicit new admission command with the inspected expected current; source verification must remain valid. Exact already-retained snapshots can be acknowledged without fresh provider effects, as in 02B.

Do not implement product creation by direct SQL from acquisition or a second writable SQLite connection. The owning store may factor common transaction helpers so review admission, job completion and their receipts commit together without nested transactions. Commands and queries retain different job/review revision scopes.

## Acquisition-v1 identity and verified admission

Preserve the reviewed provider import algorithm rather than recomputing a generic sorted JSON hash. It is SHA-256 over compact UTF-8 JSON constructed in this order: provider, host, targetProject, sourceProject, number, baseSha, headSha, sources, changedFiles. The source array and changed-file/hunk/disposition order are those produced by the reviewed acquisition adapter, not transport object property order. Each disposition is constructed as side, path, state, reason, objectId; each hunk as id, oldStart, oldLines, newStart, newLines. A hunk ID is SHA-256 of the old path string, NUL, new path string, NUL and exact matched zero-context hunk header; an absent path contributes the literal string `null`. Counts are retained outside the snapshot digest; `counts.bytes` counts acquired blob bytes before decoding/coverage rejection, not only selectable text bytes. Recompute or verify those meanings through the public reviewed acquisition port, not an independent competing hash implementation. Source fields are side, path, content, hash, objectId, lineCount; file entries are status, oldPath, newPath, oldMode, newMode, dispositions, hunks, coverage. Retain all source/object/path/mode/side/hunk fields and exact counts. Do not transform a provider value into the manual hash recipe.

Map top-level review snapshot fields from the verified candidate (target project as repository, candidate URL/number/base/head/title), retain the complete candidate plus original sources/changedFiles/counts and acquisition snapshotId. Provider state/title/branch observations are retained even where not in the identity digest. Same snapshot ID with a different canonical retained manifest remains an explicit snapshot conflict; do not silently refresh historical metadata or alter the ID to avoid it. A job can retain the differing observation for inspection.

The candidate public source-preparation acquisition adapter is implemented. It accepts trusted job inputs/effects, calls `source-acquisition/public.ts`, validates content/provenance/recipe, and returns the exact mapped snapshot plus a nonserialized witness bound to job/review/exact canonical manifest. Its constructor stays private. Raw HTTP snapshots, artifact JSON, worker status strings, or schema validity alone cannot mint it. No acquisition internals are imported into storage; the mapper consumes only public immutable values. A same-owner returned value from the trusted acquisition call is distinct from untrusted deserialized input. On recovery, re-verification follows the explicit lifecycle above before a fresh witness is issued.

Maintain reviewed acquisition effect safeguards: no shell, branch switch, source execution, install hooks, external diffs/textconv or automatic fetch. Disable lazy object retrieval, replace objects, inherited Git overrides, hooks/fsmonitor and nonliteral pathspec interpretation. Pin attribute/diff/order behavior; missing objects remain missing. Existing provider clients may perform their supported authenticated API reads, but repository configuration must not choose executable helpers to acquire absent source. Another Git version missing required flags returns unavailable; never retry with weaker flags. The import worker's cancellable effect adapter must preserve these properties when replacing the existing noncancellable Node runner.

### Representation without loss

Current 02B manual schema requires nonempty content, positive line counts, one or more sources and at most 512 source entries. Provider acquisition legitimately returns zero-line empty blobs, all-unsupported manifests with no selectable text, and up to two source sides for each of 512 changed paths. Slice03 must explicitly extend provider-specific admission to support empty strings with lineCount zero, zero selectable sources and at most 1,024 source entries. Keep empty prepared blobs and their object/hash identity; no invented line 1 or empty opposite side for additions/deletions. An all-binary/unsupported PR still has a useful complete ledger and can be reviewed, but no source-span question can target absent text.

Legacy/manual checks and IDs stay unchanged. Additive provider schema validation permits only these documented cases, still checks strict bytes/hash, source-key consistency, candidate consistency, path containment, disposition/count/hunk coherence and source-side bounds. UI comparisons and selection must handle empty/absent/unsupported sides without crashing or inventing anchors. Raw provider hunks, rather than the bootstrap line comparator, are the authoritative imported coverage spans; semantic analysis is still not performed.

## Envelope, artifacts and storage bounds

The public encoded command envelope remains at most 8 MiB including JSON metadata; existing question/reply bounds are unchanged. Acquisition defaults remain 512 changed paths, 1 MiB per blob, 8 MiB accumulated blob bytes, 4,096 hunks and 1 MiB inventory output. Raw content bytes, encoded result bytes and displayed/selectable bytes are different measures. JSON escaping can exceed either transport or artifact bounds even when raw acquisition content is within budget.

Use a small internal result reference instead of posting full source through the command envelope. Result artifacts have a separate **16 MiB encoded UTF-8 limit**, including metadata; results over it fail explicitly as result-too-large with no truncation or changed identity. Provider admissions also enforce a **64 MiB total encoded retained-source budget per review**; existing legacy data is retained, and exceeding the budget rejects only the new admission. These initial limits are declared scope, not measured scalability claims. Never delete old snapshots automatically to admit a new one.

Store artifacts only beneath the existing private external runtime data root in owner-generated import-job/invocation directories. Commands carry artifactId/digest/length, never arbitrary path. The owner maps IDs to its registry, rejects traversal/absolute paths/symlinks and verifies real containment, exclusive ownership and regular-file type. Write an exclusive mode-0600 temporary file, finish/hash/fsync it, publish without replacement using a same-directory hard link to the generated final name, unlink the temporary name and fsync the directory, then persist the matching reference. Link publication gives atomic appearance without rename’s overwrite behavior. Do not log source, remote credentials or bearer tokens. On read, open without following symlinks, bound bytes and use the same file descriptor for type/length/hash/content checks before parsing. A stored digest mismatch or observed replacement is a verification failure, not authority to reread another file. Reject unsafe existing directories rather than chmod them. Public Node24 filesystem APIs lack directory-descriptor-relative open/rename; the supported boundary is the existing private0700 single-owner root with pre/post stable-parent, no-symlink, regular-file, no-follow and same-file-descriptor integrity checks. It does not establish hostile same-UID namespace isolation against an adversary swapping parent directories. No native helper/dependency or persisted-inode attestation is introduced; restart validates registered reference/binding and current content integrity.

Artifact I/O, JSON parsing, source consistency checks and witness creation finish before admission transaction. Small result-reference validation does not lift source/schema limits. A failed artifact write leaves no admitted review. An orphan temp/final file is not a completed job; retain/reconcile by job identity rather than age, and do not guess that it was consumed. A committed admitted snapshot is authoritative even if an optional result export later disappears. Cleanup retains artifacts needed by pending/unknown/conflicted jobs; delete only task-owned disposable copies after verified knowledge/recovery reconciliation.

## Execution bounds and reactive behavior

Default single owner permits one active effect invocation and eight queued/choice/result-ready jobs; excess requests return a typed capacity result without losing accepted work. Each phase has a120-second total deadline. Discovery allows at most256 subprocess launches; acquisition and explicit re-verification allow at most4096 and acquisition's per-command timeout/output limits (provider calls up to 15 seconds; discovery Git reads up to five seconds). The deadline stops new subcommands and requests owned termination; it does not itself prove cancelled/failed. Waiting for explicit choice does not consume a live process slot. Scope/limit changes require a documented contract revision, not hidden retries or parallel spawns.

Declare public routes for import-request-committed → runner eligibility, job-committed → authorized job view and review-admitted → review view. Coalesce replaceable progress views only; accepted intents/results/receipts are durable. Remount/reconnect must not claim another invocation. Revoked/disposed UI subscriptions ignore late emissions; runner ownership is gateway/application lifetime, not React lifetime. Job completion does not enqueue an agent turn in this slice; subscribed job-terminal enrichment belongs to slice08.

## Complete ledger and graph presentation

Show provider/project/change identity, actual comparison base/head and snapshot identity; each changed path has its status, old/new path/modes, existing-side dispositions, supported hunks or explicit unsupported reason. A raw hunk has one primary ledger identity even if referenced by several graph/context views. Retain added/deleted/renamed/copied/type-changed and metadata-only/empty cases. Entire inventory failure is an unavailable import, never a shortened “complete” ledger.

Keep complete changed-file inventory, selected input, actually prepared/context source and analyzed relationships distinct. Basic slice03 imports all changed paths within declared bounds and does not require the separate unchanged-context loader. File/hunk/contains/comparison bootstrap edges remain source structure; imported material without analyzed document references says not analyzed. The manual first-120-link cap is not a complete unresolved-call/link ledger. No call graph, confirmed semantic leaf or repository test execution is claimed.

Keep all bounded ledger facts accessible while showing a readable chosen file/span/owner pair, with explicit navigation to remaining entries. Graph focus cannot retarget source selection or drafts. An import completing in the background does not move a review/history selection or replace the source behind a pending question; opening/selecting the new result is explicit.

## Verification, rationale and knowledge

Choose this design because an existing single owner already provides atomic review commands and private runtime ownership. One asynchronous runner and durable journal are sufficient for a useful bounded import; a distributed queue, worker service, generic workflow engine or new authentication layer would add scope without solving the immediate task. An artifact reference avoids weakening the transport limit or silently cutting source. Existing setup prepare is retained for recovery, while product creation gains actual authorization/receipt semantics.

Required evidence includes real-process faults around request/claim/spawn/result/admission, cancellation and restart without replay; exact ID/metadata/empty/unsupported preservation; artifact tamper/path/size rejection; comments progressing during a real import; actual React path-choice-ledger-history journey and fresh graph-first own-PR critique. Unit fixtures and GitHub success never establish live GitLab/native/human acceptance. The owning slice records candidate/target and actual results; these are verification requirements, with exact executed evidence and outstanding gates recorded in the owning slice.

At milestone acceptance, reflect on actual structure, update learned decisions/limits here and audit whole-current-product rebuild readiness from durable docs only under [round reflection](../../rules/round-reflection.md). A docs audit does not claim an actual rebuild. Passkey remains last; preserve pilot/login/data/session/routes and do not reopen native CLI investigation for this slice.


## Integration derivation decisions

The bounded implementation uses domain-owned import intent/state policy, the existing storage owner for job/review/receipt atomicity, and an import-jobs coordinator for asynchronous acquisition/process effects. Artifact I/O is an independent public boundary returning only a strict registered reference and unknown parsed JSON, never an admission witness. Its reference contains artifactId, jobId, invocationId, digest, bytes and schema import-result-v1; digest/length cover the complete compact encoded envelope (schema, artifactId, jobId, invocationId, unchanged acquisition value). Expected job/invocation bindings come from stored owner state, not the request’s arbitrary path.

New requests declare new-review or explicit same-review continuation intent. Candidate choices name an ID from a committed discoveryRevision; target choice is fixed before acquisition. A unique candidate with no existing matching review can proceed to creation automatically. Existing matching reviews require explicit selection/continuation, including legacy duplicate-review choices; a concurrent later identity collision is retained as a conflict. An explicit AdmitImportResult owner action can inspect a retained result and supply a new target/expected-current, creating a new admission attempt identity instead of altering a rejected receipt. Missing in-memory verification after restart requires explicit ReverifyImportResult and a separately journaled provider invocation, not trust in the artifact.

### Repeated identical copy-source occurrences

Reviewed acquisition-v1 can repeat a source occurrence when one base blob participates in both a modified original and a copied file. Preserve its EXACT source array/order/digest, prepared-side counts and byte accounting. Repeated (side,path) keys are admissible only when the full canonical source value (including content/hash/object ID/line count and its candidate-bound commit provenance) is identical. Conflicting values reject before admission. Manual preparation retains strict no-duplicate rules. Derive a separate unique lookup/render index for unambiguous anchors; never deduplicate the retained provider manifest or call occurrence counts unique files. Each primary file/hunk ledger still retains its own identity and copied-path relationship.

A normative real-Git case modifies a.txt while copying its original content to b.txt. The ordered ledger is modified a.txt→a.txt then copied a.txt→b.txt; ordered sources are base a.txt, head a.txt, base a.txt, head b.txt. PreparedSides is4 although there are three unique source keys. Deduplicating that array changes the reviewed identity and is incompatible. Tests must accept equivalent repeated occurrences, reject conflicting ones and derive one unambiguous source lookup while preserving both file coverage entries.


### Acquisition copy compatibility vector

A deterministic Git repository uses author/committer Compatibility <compatibility@example.invalid>, UTC date2020-01-01T00:00:00Z, base message base and head message head. Base contains a with ten original\n lines. Head changes a to changed\n followed by nine original\n lines, copies the original ten lines to b, and adds empty (zero bytes) and binary (bytes00,01). With Git2.56 defaults and the reviewed acquisition adapter, base4fedc8abc9e31d2943b08adaaa3b519b575038f7 and head0f3dee9f23ccb67a1692e8fb5502af1fde42ea61 produce snapshotf83c2d2727683f93ac10768b28b9f3791163d21da53774136fca55ac71e90dbb for GitHub github.com/team/repo change1. The four ledger paths retain five prepared-side occurrences, including base a twice, plus one unsupported binary side. Empty has zero lines and no valid question anchor. This is a compatibility data vector, not live-provider evidence.


A still-live verified result may be rebound to the same job’s explicitly chosen admission review by the source-preparation boundary using its existing opaque witness. This changes neither source nor snapshot identity. It does not accept deserialized results or a caller assertion of trust. After restart the witness is absent, so the explicit re-verification invocation remains required. Each completed invocation retains its own artifact reference even when a later re-verification produces a new one.


Storage independently enforces process ordering: discovery completion, result registration and confirmed failure/cancellation require every journaled subprocess to have an observed terminal disposition. A requested/started row cannot be ignored because a trusted caller reports a result or requests cancellation. Unresolved process state keeps the single effects slot occupied; an uncertain failure is recorded as unknown. This is a storage invariant in addition to the tracked adapter’s termination checks.


Provider comparison presentation is ledger-specific. A rename/copy pairs its old base path with its new head path; shared copied base content does not borrow the modified original’s hunks. Graph render-node identities may distinguish these comparisons while source anchors continue to identify the exact immutable side/path/lines. The raw hunk has one primary ledger entry with separate selectable side spans. Zero-line prepared blobs remain inspectable metadata, without invented line1 anchors. A review with no selectable source still shows the complete ledger, import/history controls and retained discussion.

Artifact cleanup attempts every owned handle close independently. A close-only failure after publication is publication_unknown and preserves the final file; a read close-only failure is a sanitized I/O error. Existing typed primary failures retain precedence. Neither raw filesystem errors/private paths nor publication uncertainty constitute a result/admission receipt.


The runner retains the promise of its actual active phase across ordinary scheduling ticks. No-op wakeups cannot replace that ownership record. Idle/stop await that same phase, including tracked child exit and durable terminal or unknown settlement; shutdown requests cancellation but does not report completion merely because the polling route stopped.


Observed leader exit does not establish process-group quiescence. Recovery checks the recorded owned group even for an exited leader; a live descendant keeps the invocation unknown and occupies the effects slot. It never kills a group after its ownership identity can no longer be verified. Group absence is safe evidence of stopped effects; possible group/PID reuse remains conservative rather than authorizing a kill or overlap.


A timeout/cancellation also bounds termination observation. After TERM, the tracked adapter may escalate to KILL only while the original live leader identity still verifies. If that leader exits while a descendant retains inherited pipes, the adapter settles within a further700ms as termination_unknown, detaches its read handles and retains the durable unknown slot. It does not wait indefinitely for pipe closure or infer descendant termination from leader exit. Future quiescence checks remain read-only and cannot kill an unverified/reused group.


Termination uncertainty is sticky for the entire phase, not just its latest subprocess. After an unknown outcome, the effect adapter refuses every subsequent launch even when provider discovery catches an exception and tries another route. The coordinator checks whole-phase quiescence before recording discovery completion or accepting an acquired result. A later successful command cannot clear earlier unknown effects or free their durable slot.


Runtime restart preserves the retained manual setup entry alongside any number of provider-imported reviews. The legacy source-input/snapshot exports remain that setup’s compatibility projection, not an import catalog or authority to rewrite another review. DB-only setup recovery first uses the authoritative preparation_inputs row; without one it may reconstruct a uniquely identifiable original manual review. It never chooses a provider-imported review arbitrarily. Multiple manual setup identities remain an explicit conflict. Imported reviews reopen through their exact review/snapshot URL or the explicit job result action.


The owning store maintains an additive review_import_identities lookup keyed by reviewId, with provider/host/target-project/change-number and current snapshot ID. Initial creation rechecks that lookup atomically; it does not parse every retained source aggregate to discover identity collisions. Legacy identities are populated from their retained review without rewriting source or IDs. Every review save updates the lookup in the same transaction. Content validation, witness comparison, source-budget calculation and admission request hashing precede the transaction; authoritative state/CAS checks and writes remain atomic.


## Persisted job representation and public ports

This is format import-job-v1 knowledge. SQLite remains user_version0; JSON job bodies have no additional schema discriminator. The additive physical tables below coexist with the legacy tables in persistence-compatibility.md. A fresh store has empty job/receipt/owner tables. Initialization does not start work; only the runtime’s configured import runner begins an owner generation after the existing data-root runtime lock.

| Table/key | Columns and authoritative meaning |
|---|---|
| import_jobs / id | body JSON; id equals jobId. Updates preserve insertion order for queue fairness. |
| import_receipts / id | actor, fingerprint, body JSON. Separate job command/receipt scope from legacy review receipts; id is the stable commandId. |
| import_owner / id=1 | generation: UUID for this runner ownership epoch, distinct from review attachment generation. |
| review_import_identities / review_id | provider, host, target_project, change_number, current_snapshot_id; review_id references reviews.id. Derive from retained current snapshot, treating legacy manual identity as GitHub with its existing URL host/repository/number. |

A job body retains jobId, actorId, credentialReference (SHA256 bearer verifier key, never token), path, canonicalWorktree (null before discovery), state, jobRevision, createdAt/updatedAt (UTC strings), reserved reviewId, target (null for create or reviewId/expectedCurrentSnapshotId), candidate (null before selection), ordered candidates, discoveryRevision, full bounded discovery value, existingReviews, ordered invocations, artifact (null until registered), admissionCommandId, admission (null until attempted), reason (null or bounded reason). Existing-review choices contain reviewId/currentSnapshotId and optional candidateIndex for ambiguous discovery. Public owner readback omits credentialReference and is restricted to that exact active credential/actor; job revisions are not review cursors.

An invocation retains invocationId, phase (discovery/acquisition/reverification), generation, state (running/completed/unknown/cancelled), startedAt and ordered processes; optional artifact retains that invocation’s registered result even after later re-verification. Each process retains ordinal (one-based, increasing), executable role (git/gh/glab), state (requested/started/exited), optional observed pid/startIdentity, exitCode/signal/reason, and requestedAt/startedAt/endedAt UTC timestamps as observations occur. A requested row precedes spawn. No argv, stderr or environment secrets are persisted. Exited records establish leader observations; live groups still keep phase uncertainty as described above.

The registered artifact reference has exactly schema import-result-v1, artifactId, jobId, invocationId, digest and bytes. Its bytes/hash cover the full encoded envelope, not just source text. The envelope’s value is the original full acquisition result. It grants no source trust. IDs for jobs, reserved new reviews, invocations, artifacts and ownership epochs are generated UUIDs and retained before the effects they identify; source snapshot IDs retain their separate versioned digest scheme. Process ordinal belongs only to its invocation.

## Corrected bounded integration decisions

The initial256-launch import ceiling rejected the actual49-path PR23 at256 observed exits despite a complete public acquisition requiring261 Git and2 gh commands. The import-only ceiling is now4096, retaining discovery256, total120-second phase deadline, one active invocation, queue8, per-command/source/artifact bounds and all fixed-executable/no-target-execution protections. This is a bounded policy correction, not a new Git algorithm or source identity. A calculated worst-case successful acquisition uses5 Git setup calls (type+commit for each pin and one raw inventory), at most3 reads per1024 existing sides, at most1 patch per512 paths and up to3 provider refresh calls:5+3072+512+3=3592. GitHub’s2 provider calls give3591; GitLab’s3 give3592. Unsupported routes can stop earlier. Observed PR23 used5+3×69+49=261 Git calls plus2 gh; it does not prove worst-case runtime performance. An injected owner test limit may only lower these ceilings, never enlarge them or arrive through HTTP/environment.

Retained-source quota has one exact representation: sum UTF8 byte lengths of compact JSON.stringify(snapshot.sources) for every retained snapshot, preserving source occurrence/array order, source member names/values and ordinary JSON escaping. An empty source array costs2 bytes. This is the encoded source-array quota, not a whole review/DB/ledger quota and not raw content bytes. An exact boundary is allowed; one byte over rejects only the new admission. Exact already-retained acknowledgements add no second charge. Preserve over-budget legacy/history records and all prior IDs/current/question/credential/receipt state; no eviction or re-encoding to fit. Validation/source sizing occurs outside the effectful transaction; authoritative retained state and current CAS still determine atomic apply. Owner-only test constructors may lower the byte limit for exact boundary cases, not raise the64MiB product maximum. The store constructor accepts an optional importLimits object with maxLaunches (integer1–4096) and maxRetainedSourceBytes (integer1–67108864); omitted values use the product maxima. The launch override is additionally capped at256 for discovery. These options are internal test/control inputs, absent from HTTP and environment configuration; invalid values reject initialization.

In-pane line selection preserves the currently displayed copy/rename comparison when the chosen source belongs to that comparison. It changes only the immutable anchor’s selected line range; it does not drop the private comparison key and substitute another After path. External saved-anchor reopening may still require choosing a shared comparison again. No comparison key is added to persisted question anchors or source hashes.

The import bridge’s reads and command publications belong to a credential/generation and connection lifetime. Explicit login starts a new generation, clears the previous active view/intent recovery and does not let an old request publish jobs/errors or clear a newer pending command. A command already sent may still commit server-side; this is not rollback or permission to resubmit it as a new credential. Disposal invalidates/aborts only owned reads; reconnect rereads authorized state and old completions remain fenced. Regular polling does not replace an explicit login/readback read or acquire source. Active-connection teardown is idempotent and cannot invalidate a newer connection. A command dispatched before teardown may have committed: disposal keeps its unchanged-credential retry intent but fences late publication; reconnect rereads authorized state and exact retry keeps the same command ID. Explicit login, even to the same token, deliberately starts a new credential generation and clears prior scoped intent recovery; this does not undo any server receipt.

Exact provider candidate/value/enums/nulls/ordering and complete hash-input data are maintained in [acquisition compatibility](acquisition-compatibility.md). This supersedes references to an old adapter as the sole definition of hash-bearing fields.

## Journal-loss quiescence correction (05E)

A terminal journal label is a leader observation, not proof that no process was spawned. If persisting `started` fails after a durable request, the child may already own live descendants. Every later terminal observation must repeat the actual observed pid and startIdentity when available, even when the earlier start write failed. Journal uncertainty remains sticky in the adapter; retaining identity permits safe read-only reconciliation, not immediate success or signaling an unverified group.

Add optional private process field `spawnDisposition: not_spawned` only for a definitive spawn-error event before any start was observed and with no child PID. This is additive to existing records; absence means no such proof. Reject contradictory not_spawned observations (started state, observed pid/startIdentity or previously started/pid-bearing journal). A legacy exited record without pid and without that explicit proof remains unresolved. Do not infer not_spawned from its reason string, exit code, missing identity or omitted field. Existing receipts, admitted results and source/history remain unchanged.

A shared pure process-journal eligibility predicate admits read-only reconciliation only for (a) started/exited with a positive safe observed PID, requiring a fresh absent owned-group observation, or (b) exited with explicit not_spawned and no contradictory identity. Requested-only and ambiguous missing-PID rows retain the unknown barrier. Both import and semantic coordinators use this rule; storage independently refuses confirmQuiescent when any retained process lacks this minimum evidence. An empty journal may settle only under the existing durable-request-before-spawn contract, which proves no instrumented effect was launched. Earlier ambiguous processes cannot be hidden by later complete observations.

Reconciliation never signals a missing/reused/unverified identity. A live group keeps the shared lease, even when its leader exited. Once positive group absence is observed, stopped effects can be recorded without inventing a successful result or replaying the interrupted invocation. Failed terminal journal persistence leaves the original requested/started record and uncertainty intact. Current owner/epoch fences remain mandatory for every store mutation; cancellation/shutdown still settle only the actual owned handles within existing limits.

The correction's shared domain/public function is `processQuiescenceEligible(record)`, where the record contains state and optional pid/startIdentity/spawnDisposition. It performs no OS effect and rejects unknown spawn-disposition values. `import-jobs/public.processQuiescent(record)` applies that minimum rule and, for an observed PID, performs the existing read-only group-existence probe. Both coordinators call it; both stores recheck minimum eligibility before confirming an unknown invocation. Storage still relies on its private current owner for the fresh group-absence observation and does not execute an OS probe inside a transaction. `not_spawned` is accepted only on an exited observation replacing a requested row with no prior observed PID/startIdentity. No persisted schema rewrite is required; old ambiguous records remain unknown instead of being silently upgraded.
