# Pinned source acquisition

**Direction:** Accepted acquisition and bounded unchanged-context preparation scope

**Context contract:** `pinned-typescript-context-v1`

**Implementation status:** Context port and integrated core/React candidate independently reviewed with trusted snapshot/corpus witness and mapping tests. Actual ownPR understanding and full slice acceptance remain open.

**Parents:** [Review loop](README.md), [import boundary](evolution.md#import-boundary-v1)

## Responsibility and authority

Acquisition turns explicitly pinned Git objects into retained immutable values. Review-domain admission owns durable review state. The existing discovery/import port resolves provider metadata and accounts for changed paths; unchanged-context loading is a separate public operation. It does not open the review database, select a function, produce a call graph or change an existing snapshot. Later integration uses both ports through declared public boundaries, outside short transactions.

`loadSourceContext(input, effects)` accepts the selected snapshot ID, declared provider/host/source-project/target-project/change identity, explicit base/head commit IDs, a local worktree locator, optional per-side priority paths and lowered budgets. The locator finds Git objects; its live text, configuration files and dependencies are never source inputs. Context loading verifies Git object provenance, but does not independently authenticate the declared provider identity or rediscover/rebaseline a PR. Its result labels that distinction. Admission must compare its declared identity and commits with the authorized snapshot.

The context port supports the accepted `source-neighborhood-v1` TypeScript/TSX corpus requirement. It does not depend on that analyzer or a compiler package. Both sides are acquired independently, including unchanged caller/callee candidates and declaration-only `.d.ts` files. No actual caller/callee or seed function is resolved here. Supplied priority paths identify required source files, never substitute a different function by name.

## Safe Git reads

All commands use fixed executables and argument arrays through the existing injected acquisition effects. Production effects remove inherited Git overrides, disable lazy fetch, replace objects, optional locks and prompts, and do not return raw command errors or credential-bearing remote values. A missing promised object remains missing: no fetch, remote helper, hook, filter, textconv, checkout change or target execution is authorized. The importer also uses literal pathspecs and deterministic pinned-attribute text diffs; context loading needs only raw object reads and never invokes a diff driver.

Verify both commit objects and every traversed tree/blob against its Git object ID, including object type. Enumerate directly from verified tree bytes, preserving strict UTF-8 repository-relative names. Read each selected regular blob exactly, verify its Git object hash, decode UTF-8 strictly with BOM preserved, and retain SHA-256 content hash, object ID, side, commit and exact text. Symlinks are metadata only and are never dereferenced. Gitlinks are explicit submodule boundaries and are never traversed. Binary/malformed UTF-8 source remains unsupported. Empty source is valid retained text. No live `tsconfig`, aliases, package configuration or generated files are read; future configuration requires a separate explicit pinned input.

## Inventory, selection and retained corpus

Return separate values for known inventory, selected paths, preparation/exclusion ledger and retained text. Each known TS/TSX path records side/commit/path, object ID/mode, `changed`, `context` or `declaration-only` role, independent change knowledge, priority/selection flag and its actual preparation or exclusion reason. A known tree/submodule boundary also has a ledger row when descendants are unavailable or unsupported. No excluded or unknown path establishes zero callers or a leaf.

Tree enumeration is bounded. Each side reports complete/incomplete traversal, known source and boundary counts, and unknown unvisited counts when traversal was stopped or unavailable. A complete inventory means the pinned superproject tree was enumerated, not that submodule contents or external consumers were inspected. Never label a bounded prefix a complete repository inventory. Inventory order and selection are canonical by side/path, independent of request priority ordering.

Required priority sources are selected first across both sides, followed by remaining paths in canonical order, within the per-side prepared-text quota and combined byte budget. Required paths that are absent, not enumerated, unsupported, missing or over budget make the result unavailable, retaining the observed ledger. Do not silently select another file. Non-priority paths beyond the selection quota or byte budget retain explicit exclusions; selected but unpreparable sources retain their own missing/unsupported reason. Enumerated paths outside `.ts`/`.tsx` need not be loaded as text; their observed counts are separate from known supported sources. Declaration files remain explicit declaration-only inputs, not implementation bodies.

Inventory and selection completeness are distinct. The accepted analysis contract separates up to 4096 known inventory rows per side and 2 MiB combined ledger metadata from the 128 prepared-text entries per side. Content-less exclusions/missing/unsupported rows do not consume the prepared-text quota. Keep the whole bounded known ledger when mapping to analysis; passing a shortened list must never claim that absent paths were scanned. This operation does not import analyzer internals.

Prepared results can retain incomplete source scope with explicit accounts and exclusions. Invalid identity/commits or unavailable required priority source produces an unavailable result, not a consumable success corpus. Both result forms retain bounded observed coverage. No parse, invocation or caller count is invented: acquisition has not examined such facts.

## Profile, limits and identity

The fixed profile is `pinned-typescript-context-v1`. Defaults are 128 prepared source entries per side, 256 KiB per source blob and 4 MiB combined source bytes, compatible with the analysis defaults. Additional traversal bounds are 4096 tree entries per side, 256 tree objects per side, 1 MiB aggregate tree bytes per side and 2 MiB combined ledger metadata. Metadata accounting reserves room for each known row's longest status fields before admitting that row, so later preparation cannot push the ledger over its cap. Each command has a 15-second deadline and commit metadata has a 1 MiB cap. Callers may lower these bounds; attempts to raise them reject. Content-less unsupported/missing/excluded rows do not consume the prepared-source quota. The byte budget counts bytes actually retained from verified blobs, including unchanged bytes separately for each side.

The context corpus identity is content-derived from contract/profile, snapshot and declared repository identity, pinned side commits, normalized priorities and budgets, side accounts and the canonical ledger/text hashes/object IDs. Exact text is retained, not replaced by mutable filesystem references. Reordering priorities does not change the result. Same bytes on opposite sides keep separate side/commit identities. Changing content, a side, an exclusion or a budget changes the corresponding corpus identity. Do not replace the review snapshot ID with this digest; analysis/admission must carry both.

Results are deeply frozen; caller input is neither mutated nor frozen. No credential, worktree locator, host-session metadata or provider authentication diagnostic enters the retained corpus. The locator does not affect identity, so the same verified objects acquired in another checkout yield the same corpus.

## Verification and limits

Require disposable real Git fixtures for unchanged source on both sides, declaration-only source, exact bytes/hashes, deterministic ordering/identity, missing promised commits/trees/blobs without helper execution or retrieval, binary/symlink/submodule boundaries and lowered file/byte/enumeration limits. Priority failures must be explicit and enumeration truncation must leave unknown counts unknown. Keep changed-file import regression checks passing.

Source preparation is not independent engineering acceptance, imported-source admission, a durable job, React graph/E2E evidence, actual own-PR comprehension, native-host acceptance or a claim of exhaustive hostile-repository containment. Root owns those later checks and durable docs-only rebuild review. Record observed preparation results and verified limits here after implementation and reconcile material review findings before acceptance.

## Context public values and adapter mapping

Input requires `snapshotId`, `identity` (provider, host, sourceProject, targetProject, positive change number), `commits.base`/`commits.head`, `worktree`, and optional `priorityPaths.base`/`priorityPaths.head` and lowered budgets. Priorities are deduplicated and sorted; unsafe/non-TS paths and impossible priority counts reject before effects. Commit IDs must be full SHA-1 or SHA-256 object IDs of the same format, not branch/ref names. Declared host/project values are validated and projected; extra input properties are not retained.

The public result has `kind: prepared|unavailable`, `corpus` and typed `issues`. Invalid request values return unavailable with null corpus and no Git commands. Failed commit validation or any unavailable required priority source returns unavailable with the observed corpus/ledger where possible. A prepared result may still have incomplete enumeration or unprepared non-priority paths; read its accounts/ledger, not just its kind.

The corpus contains contract/profile/provenance labels, original snapshot ID, declared identity, both commits, normalized priorities/budgets, per-side accounts, the canonical ledger, exact retained sources, observed byte counts and `corpusId`. Ledger rows contain side/path/commit/objectId/mode, source versus tree/submodule-boundary kind, role, separate changed/unchanged/unknown knowledge, priority/selection flags and preparation (`prepared`, `excluded`, `missing`, `unsupported`) with reason. `selected` means preparation was requested or attempted, not proof of retained text or a compiler scan. A path with no verified counterpart in an incompletely enumerated opposite side has unknown change knowledge; it is not guessed added/deleted. Declaration-only role remains explicit even when the declaration file changed.

Each retained source has side/path/commit/role, selected=true, exact content, contentHash (SHA-256 of original UTF-8 bytes), Git objectId and actual lineCount. Empty content has zero lines. BOM, CRLF and astral Unicode are preserved. All source text counted by `filesPerSide`/`totalBytes` is retained text; content-less exclusions do not consume that quota. Git may read a bounded blob before discovering it is binary/invalid or cannot fit the combined retained-text budget. No total bytes-read, RSS or latency guarantee is inferred from a retained-text bound.

Accounts report pinned commit, inventory scope, enumeration status, known source/boundary counts, observed tree-entry/object/byte counts, unvisitedPaths (zero only after complete traversal; otherwise null), and prepared/excluded/missing/unsupported known-source counts. Tree-entry limits count all traversed entries, including directories and non-TS paths; metadata and tree limits can therefore stop before the supported-source count reaches its cap. Known submodule boundaries remain unsupported without claiming their descendants were enumerated. Missing/tree/hash/type/UTF-8 and budget failures are kept at the known side/path; unknown descendants are never replaced with invented per-file counts.

The adapter to `source-neighborhood-v1` joins retained sources to ledger rows by side/path. Preserve every known source and boundary row as an analysis SourceEntry or explicit account exclusion, map acquisition prepared/excluded/missing/unsupported meaning without claiming parsing, and carry the exact side commits. `inventory: repository-enumeration` is allowed only for complete verified traversal; otherwise use selected-context. The analysis input's `acquisition` string records `pinned-typescript-context-v1`. Analysis has its own canonical representation, profile/configuration and corpus/analysis digests; the acquisition corpusId is separate retained provenance and cannot be passed as an invented analyzer digest. The selected review snapshot ID remains unchanged. Root must reconcile the exact mapping and metadata measurement at the integration boundary, not import subsystem internals.

### Regular-mode and minimum-metadata boundary

Only canonical regular-file modes `100644` and `100755` are eligible for prepared source text. Hash verification and blob type are necessary but do not make an unknown/noncanonical tree mode a regular file. Known TS/TSX paths with other unrecognized modes retain `unsupported/object_type` and no source text; exact symlink/gitlink modes retain their specific exclusions. Required paths with those dispositions fail explicitly.

The minimum accepted `inventoryMetadataBytes` is two, covering the serialized empty ledger `[]`. A one-byte cap rejects as invalid input before any Git effect and returns no corpus. Accepted caps include all actual serialized ledger bytes; an empty ledger does not waive that bound. Independent review identified both clarifications at context source `1d11a05`; correction verification is recorded below.

**Observed correction verification:** Two new tests reproduced both failures before repair. The corrected module passed **27 combined acquisition/context tests** and scoped strict TypeScript. Real hash-verified raw tree entries with `120001`, `100600` and `040001` modes retain unsupported/object_type rows without source text, including explicit required-path failure. A one-byte metadata cap rejects before effects; the two-byte minimum retains an exactly two-byte empty ledger with truthful incomplete scope. These checks correct the reviewed boundaries. Independent targeted recheck completed before incorporation; the combined module suite contains11 context and16 changed-file tests.

## Exact retained corpus identity

`corpusId` preserves the reviewed loader's ordered compact JSON recipe; it does not use semantic canonical key sorting. SHA256 hashes the UTF-8 serialization of these fields in order: contract, profile, provenance, snapshotId, identity, commits, budgets, priorityPaths, accounts, ledger, sources, observed. Omit corpusId itself. In sources only, omit content while retaining each hash and provenance field. Issues are retained separately and bound by the trusted wrapper; they are not an extra corpusId input. Persisting records canonically must not change an already verified corpusId or re-create trust from serialized JSON.

The normalized nested field order is part of that legacy recipe:

- identity: provider, host, sourceProject, targetProject, number; side maps always base then head.
- budgets: filesPerSide, fileBytes, totalBytes, inventoryEntriesPerSide, inventoryMetadataBytes, treeObjectsPerSide, treeBytesPerSide, timeoutMs. Lower overrides replace values without changing that order.
- each side account: commit, inventory, enumeration, knownSourcePaths, knownBoundaryPaths, observedTreeEntries, treeObjectsRead, treeBytesRead, unvisitedPaths, preparedSources, excludedSources, missingSources, unsupportedSources.
- each ledger row: side, path, commit, objectId, mode, kind, role, change, priority, selected, preparation, reason.
- each digest source row: side, path, commit, role, selected, contentHash, objectId, lineCount.
- observed: sourceBytes, ledgerMetadataBytes.

Ledger/source arrays sort by raw lexical side then path; priorities deduplicate and sort by raw lexical path. Source contentHash is SHA256 of the exact verified UTF-8 blob bytes, without BOM/newline normalization. A Git object ID hashes its raw type, ASCII space, decimal byte length, NUL and exact object bytes using SHA1 for40-character IDs or SHA256 for64-character IDs. Empty text has lineCount0; nonempty source lineCount counts LF-separated lines, omitting the trailing empty entry after a final LF. Semantic parser line coordinates remain a separate meaning.

## Loader value and byte compatibility

The ordered hash input above has contract and profile both exactly `pinned-typescript-context-v1`; provenance is the string `declared-provider-verified-git`, not a nested object. `identity` contains provider (`github`/`gitlab`), lowercase host, sourceProject, targetProject and positive integer number. `commits`, `priorityPaths` and `accounts` always contain both base and head. Missing priority input normalizes to an empty array for that side. Corpus fields are always present; an unavailable result may instead have corpus=null. The result wrapper has kind prepared/unavailable, corpus and issues (always an array). Issues are not embedded in the loader corpus.

| Value | Exact representation |
|---|---|
| Side account | All fields in the ordered recipe are required. inventory=`repository-enumeration` only after complete traversal, otherwise `selected-context`; enumeration=`not_started`/`complete`/`incomplete`. Counts are nonnegative integers. unvisitedPaths is0 for complete enumeration and null when unknown, never a guessed count. |
| Ledger row | Every ordered member is present. side=base/head; commit/objectId are hexadecimal Git IDs; mode is the six-character octal Git mode. kind=source/tree/submodule; role=changed/context/declaration-only; change=changed/unchanged/unknown; priority/selected are booleans. preparation=prepared/excluded/missing/unsupported. No row content or absent-field shorthand exists. |
| Prepared source | Every ordered source member is present, including content between selected and contentHash in the full value. selected is true. role uses the ledger vocabulary. content is exact UTF-8-decoded text; contentHash is lowercase64-hex SHA256; objectId is the verified Git blob ID. The hash-input source row omits only content. |
| Issue | reason is required; optional side, path and limit are omitted when absent, never serialized as null. limit, when present, is an exact ContextBudgets key from the ordered budget recipe. |

The complete ledger reason vocabulary is `text`, `empty`, `not_selected`, `source_limit`, `file_limit`, `total_byte_limit`, `binary`, `invalid_utf8`, `symlink`, `submodule`, `missing_object`, `object_type`, `hash_mismatch`, `tree_limit`, `tree_byte_limit`, `inventory_limit`, `inventory_metadata_limit`, `invalid_tree`. Issue reasons additionally permit `invalid_input` and `required_source_unavailable`. A directory boundary uses kind=tree, mode=040000, role=context, change=unknown, priority=false and selected=false; its preparation is missing for missing_object and unsupported for other boundary reasons. A submodule uses kind=submodule and reason=submodule. A regular unselected source begins excluded/not_selected; a file-count exclusion uses reason=source_limit. `.d.ts` has declaration-only role. No descriptive synonym is compatible with these hash-bearing literals.

There are two distinct loader metadata measures. Before adding each ledger row, reserve its compact JSON UTF-8 byte length after replacing role with declaration-only, change with unchanged, priority and selected with false, preparation with unsupported and reason with inventory_metadata_limit, keeping all other row values and the ordered member positions. The running reserved measure starts at2 and adds that transformed row's byte length plus1 for every accepted row, including the first. A row is not recorded in the ledger if that addition exceeds inventoryMetadataBytes; traversal records the corresponding issue and incomplete scope. This conservative measure intentionally reserves one extra comma byte overall for a nonempty ledger. It bounds later status changes but is not reported as observed usage.

The final observed.ledgerMetadataBytes is exactly the UTF-8 byte length of compact JSON for the actual final sorted ledger array, including brackets, commas and all actual status values. It is2 for an empty ledger. observed.sourceBytes is the sum of exact prepared source UTF-8 byte lengths, counting each side occurrence. Both observed values enter corpusId. The analyzer's inventoryBytes is a different canonical source-metadata measure defined in [semantic protocol values](semantic-data.md).

The complete [data vector](semantic-data-v1.json) contains an ordered loader hash input from a controlled real-Git fixture with a prepared BOM/CRLF/astral source and a second excluded source. Its reported ledgerMetadataBytes is565, reservedMetadataBytes is628, and corpusId is `601ba2201ea742a1e70bad923550ca60480d86a3c0ccd323b1bf8d3449d4c27d`. Recompute the digest from loader.hashInput using its stored construction order and compact JSON; sourceContents supplies the omitted text separately. This is protocol conformance data, not admission authority or live-provider evidence.
