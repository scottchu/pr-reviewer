**Date:** 2026-10-24

**Direction:** Bounded slice04 core, worker and React independently reviewed; combined candidate checks pass. Actual ownPR understanding and full acceptance remain open.

**Scope:** Verified pinned TypeScript/TSX context, static one-hop neighborhoods, readable comparison and durable source clarifications. Story playback and execution comparison are later scope.

## Experience and meaning

From an immutable review snapshot, choose a changed function and inspect before/after callers and callees, including unchanged source. Each static edge opens the actual same-side call site, implementation declaration and any import/re-export/overload evidence. Source inspection is an explicit action; graph focus, expansion, background completion and history polling never change a question anchor or draft. Retain the original source/graph selection and return position when following evidence.

Show what is known before asking the reviewer to reconstruct it: selected declaration, side, changed/context role, static method, outgoing uncertainty and the scope of the incoming search. The view uses the existing React Flow dependency, one selected function and optional comparison partner, and at most twelve initially visible nodes. All bounded neighbors, call sites, unresolved sites, diagnostics and coverage rows remain accessible through labeled lists and keyboard controls. Remaining visual counts are exact within admitted facts; they are not omitted-repository counts. Do not fit the whole corpus onto one unreadable canvas.

Before/after comparison is a presentation relation, never a call or proof that two functions are equivalent. A source-informed user explicitly selects each side from exact declarations. A same-path/name suggestion may be a labeled navigation suggestion but cannot silently pair renamed/ambiguous declarations. Missing, added, deleted or unsupported counterparts stay explicit. No line/name overlap becomes a semantic identity. A first useful view can show one selected side while a comparison partner remains unselected.

Confirmed edges retain `ts-static-binding-v1` / `resolved_static`, conditional syntax and exact evidence. Static binding does not prove runtime execution, reachability, behavioral intent or test success. Unsupported dispatch, mutable bindings, external/missing modules, declaration-only targets, aliases/config gaps, JSX/framework invocation and analysis limits remain visible. Candidate declarations are not edges. No incoming matches means only “No resolved callers found in these supplied files.” A leaf label is allowed only when the core supplies “No explicit invocation sites in this function body under the supported syntax scan.” Neither statement proves no effects, outside consumers or indirect behavior.

Reuse the existing single host, lock, SQLite transaction/receipt helpers, registry and hardened process ownership rules. Do not turn the import coordinator's `ImportGrant`, import states or `import-result-v1` artifacts into analysis authority. Import invocation and analysis invocation have separate IDs, generations, typed results and schema. A small store-owned effect-slot lease serializes source-import effects and context/analysis work: one active resource-consuming invocation globally, up to eight pending analysis jobs, no transaction while waiting. Choosing a declaration releases the slot. Comments and graph writes use independent short transactions. Unknown ownership blocks the effect slot until reconciled, not discussion. This is a narrow shared lease, not a general scheduler/service.

The lease is new integration behavior: the predecessor import store serializes imports only. One private owner-held SQLite row records owner epoch, effect kind, job/invocation and phase. Initialize its owner epoch once before either runner claims; a runner must not reset the other runner's ownership. Acquire atomically with the corresponding job claim and release only for that matching definitive terminal/quiescent invocation. Startup reconciles existing import/analysis unknown states before any claim, including legacy jobs without a lease row. Missing lease data never proves no process is running. Preserve import's own opaque grants and process journals; expose only the narrow owned observation/cancellation/limit port needed by context acquisition. This does not create general scheduler policy.

## Immutable identities and source admission

Keep manual and provider snapshot IDs and their historical bytes unchanged. A corpus supplements a snapshot; it is never appended into `Snapshot.sources` and never rehashes the review. Persist a separate context record keyed by reviewId/snapshotId/corpusId with exact loader contract/profile, declared identity, both commits, priorities/budgets/accounts/ledger, source bytes/hash/object IDs and issues. The loader's `corpusId`, analyzer's `corpusDigest`, analyzer's `analysisId`, job ID and graph revision are distinct.

Provider snapshots use their retained candidate identity. Their admitted import path may supply the locator, but locator existence does not establish source trust. A user may explicitly supply a replacement local worktree containing the same pinned objects. Historical snapshots analyze their retained commits without refreshing provider heads or switching current history. Legacy manual snapshots have no trusted source-project metadata: the owner must explicitly provide a declared sourceProject with the locator; provider/host/target-project/number must match the existing public snapshot review identity. Label this declared identity, not newly verified hosting metadata. Do not guess a fork/source project, migrate the snapshot or invoke provider discovery as a prerequisite. Agents cannot supply/change filesystem locators.

Provider source manifests may repeat identical (side,path) occurrences for copied files. Preserve their exact order, multiplicity, source quota and snapshot digest. Compare every overlapping occurrence against one unique context source; equivalent repetitions do not become duplicate analyzer SourceEntry rows. Conflicting occurrences reject. Copy/rename comparison identity remains separate from the shared source anchor; context and semantic pairing cannot silently pick the modified original instead of the selected copy. Empty or unsupported sides offer no invented declaration/line1.

The wrapper validates exact snapshot membership and both commit pins, the loader corpus digest, all retained text hashes/object provenance and all overlapping side/path snapshot source bytes. A disagreement rejects the corpus, never substitutes the newer text. New context evidence remains addressable after checkout edits/removal or app restart. Loader required-priority failure or unavailable status produces a retained failure account, not a successful context witness. Prepared with incomplete enumeration remains usable only with its explicit limitations.

### Mapping coverage without broadening it

Retain the complete original loader account and ledger. For the analyzer, map every known source row to one `SourceEntry` with exact side/path/commit/role. Join retained bytes by side/path; prepared selected sources remain selected, content-less excluded/missing/unsupported sources retain their exclusion and selection meaning. Never substitute selected=true for prepared=true. Tree/submodule boundary rows stay in the retained acquisition account and public coverage view; they are not fake source files passed to the parser. Preserve unknown descendants and their boundary reason; do not fabricate per-file exclusions. Analyzer input scope is `repository-enumeration` only after complete verified traversal, otherwise `selected-context`, with acquisition method `pinned-typescript-context-v1`.

Revalidate the mapped input independently. Loader `inventoryEntriesPerSide=4096` counts traversed directories and non-TS entries as well as supported source; analyzer `inventoryPathsPerSide=4096` counts supplied known source rows. Loader 2 MiB metadata reserves row status space; analyzer 2 MiB measures its canonical projected source ledger. These are different counters, not interchangeable quotas. If projection exceeds analyzer bounds, record unavailable with both observed accounts; do not truncate the mapped ledger to force success. Excluded inventory can exceed 128 rows: only prepared source counts toward 128 entries per side, 256 KiB/file and 4 MiB combined retained source. Keep complete changed-file inventory, requested priorities, prepared source, selected analyzer input, actually scanned source and visible graph projection separate in queries/UI.

The first integration uses `repository-static-v1` without configuration. No live or pinned tsconfig extraction is added here. Relative supplied TS/TSX modules work within the reviewed profile; alias/configuration-dependent sites remain unknown. The pure module's optional pinned alias support remains available as preparation capability, but no arbitrary UI alias JSON is accepted. A later configuration acquisition contract is needed to use it in the product.

Importing a new snapshot neither retargets an old job nor cancels valid historical work. Jobs for retained history may finish into that history; the current visible view changes only by explicit selection. Analysis result admission checks exact job/invocation/owner generation, current requested snapshot generation, credential authority, no committed cancel and exact corpus/input/result identity. ### Explicit bounded context preparation

The owner may lower contextFilesPerSide to1–128, paired with exact per-side priorityPaths to prepare a bounded investigation. Omission preserves the existing128-per-side behavior. The cap bounds successful prepared source entries on each side; it is not an exact allowlist and never changes the complete known inventory. Required priorities are deduplicated and sorted by the loader; each side's unique required-path count must fit the cap. The strict command schema rejects an excess before creating a job, receipt or generation change. Duplicates remain in the parsed command fingerprint but consume one required path; submitted order remains part of retry identity even though loader normalization is deterministic. Existing combined64 submitted-priority-entry limit remains unchanged.

Priorities are prepared first; remaining successful slots follow the loader's deterministic order. To investigate an exact pair of files per side, explicitly require those files and choose cap2. A side with fewer required files may also prepare other paths until its cap is filled. Only explicit priority paths are required: being an imported changed/prepared Snapshot.sources path does not automatically make a path required in the separate context corpus. A capped investigation may exclude that path while retaining its ledger row and original snapshot evidence. Overlapping selected bytes must still exactly match every original snapshot occurrence. Missing/unsupported/over-budget required files make context unavailable; no unrequested replacement can satisfy requiredness. All other file/byte/metadata/tree/process/worker limits remain unchanged. sourceProject remains declared repository identity and worktree remains a locator; neither filters paths.

The complete context ledger retains other known sources as excluded/source_limit when successful-file capacity is exhausted, with no source bytes fabricated for them. Original Snapshot IDs/bytes/current source and previous outcomes remain unchanged; the capped context is a separate immutable corpus. Its budgets.filesPerSide value and selected/excluded ledger participate in corpusId. Complete enumeration does not mean every source was prepared or scanned. Static caller/leaf statements remain scoped to the supplied selected source and retain incomplete-coverage limitations; an excluded caller cannot justify a repository-wide no-callers claim.

This amendment follows a real whole-PR inventory exceeding the unchanged10000 invocation-site bound. Inventory legitimately scans invocation syntax under the same AST/site budgets even though it does not bind calls. A narrower explicit source preparation is a supported next request, not quota relaxation or a partial graph from the failed attempt. The previous unavailable inventory/job remains retained. The UI must present the cap and per-side required paths explicitly, show their effect on prepared versus complete-known coverage, and never silently treat priority input as an allowlist.

Semantic command receipts explicitly contain commandId, actorId, applied/rejected state, reviewId, snapshotId, analysisGeneration, current graphRevision, optional jobId/jobRevision, result and optional typed error. These are not import/review receipts with a renamed revision. A read-your-write query supplies the relevant graph/job minimum independently; it cannot satisfy that minimum with an unrelated review revision. Maintain an independent graphRevision per review+snapshot, initially 0. Successful fact admission and successful clarification updates each increment it once; unrelated question/reply/review revision changes do not. Fact admission CAS uses expected analysis generation, not an old graphRevision, so a concurrent clarification is preserved and the next graph revision is assigned in the same transaction. A clarification targets the selected admitted analysisId and exact expectedGraphRevision; stale version or another selected analysis yields `graph_conflict`, with no partial mutation. Previous-analysis clarifications remain immutable readable history and are never silently reanchored to new facts. The user can explicitly create a new clarification citing prior provenance.

User and currently attached agent may clarify within their authorized review. Bootstrap cannot. Check agent attachmentId/generation and revocation at apply time even when an exact command receipt exists; do not grant a revoked token readback through replay. An agent edits only its own clarification; the user may correct any by appending a revision with preserved original author/history. All edits preserve immutable primary anchor/analysis identity; changing anchor creates a new clarification with supersedes provenance. Evidence anchors must exist in admitted same-analysis source; interpretation is visibly attributed and cannot promote unresolved to resolved. Ordinary clarification commits emit no notification/inbox/wake. Agent access is through the normal public domain/MCP command boundary, never arbitrary graph JSON or raw database writes.

## Durable execution and failure policy

Persist jobId, owner credential reference (never bearer token), review/snapshot, analysis generation, request fingerprint, locator in owner-only job data, priorities/profiles/budgets, jobRevision, corpus/inventory/result references, and invocation observations. Distinguish context Git invocation, declaration-inventory worker invocation and neighborhood-compute worker invocation. Each has a fresh invocationId, app ownerRunId, private nonserialized phase grant and launch/start/exit/result observations. Public input cannot create a grant. Known result validation happens outside transactions; admission and receipt happen in one short transaction. The trusted worker wrapper checks schema/version, exact input fingerprint and snapshot/corpus/analysis identities, unique node/site references, source hashes/offset/line ranges and bounded coverage before minting its private witness; raw child JSON or an HTTP payload alone is not admission authority. The wrapper binds the witness to the exact normalized immutable input and invocation; persisted verified corpus records can be read for later phases without treating an uncommitted staging artifact as verified.

Lifecycle: queued context → context running → retained verified corpus → inventory worker → awaiting declaration choice → compute worker → validated result → atomic admission. Each boundary is committed before the next effect; no process or user choice holds a transaction. Retain unavailable/unsupported/budget outcomes as outcomes with coverage, never a partial success graph. Cancellation prevents further phase launch. A result message and child exit are separate observations; validate a complete result and confirm clean owned termination before admitting. Sticky unknown across the entire invocation cannot be reset by a later successful subcommand or provider fallback.

Context uses the reviewed hardened Git effect policy, raw pinned object reads only, no fetch, helper, target code, hooks, filters, config execution or ambient Git overrides. Reuse process-policy implementation only after exposing a narrow public tracked-effect port independent of ImportGrant; do not import its internals or weaken it by passing a fake grant. Give context phase 120 seconds and at most 2048 subprocess launches (separate from import discovery256 and acquisition/reverification4096). The reviewed loader uses three Git reads per object: type, size and bytes. This is a deliberately narrower integration envelope, not a guarantee that all default loader corpora fit: two commits, up to512 trees and256 successfully prepared blobs alone allow2310 reads, and rejected candidates may consume further reads before successful-source quotas are reached. Each command keeps the loader's maximum 15-second timeout and byte cap; exceeding phase limits is explicit unavailable/unknown according to confirmed termination, not permission to raise source quotas. On the2049th attempted launch, stop before spawning and retain `phase_limit` as unavailable after confirmed quiescence, or unknown when termination is unconfirmed. No partial context/graph success is admitted. If the loader did not return an account, mark traversal/preparation outcome unavailable with unknown unvisited coverage; do not fabricate a complete ledger or zero callers from process counts. If it returned an unavailable required-priority result, retain that known ledger and exact required-source failure. This limit stays independent of import limits; actual ownPR evidence must fit it or record the measured failure and next action before any proposal to change it.

Run pure inventory/analysis in a fresh owned Node child process, not gateway/UI thread. Launch only the app-owned fixed worker entry using the current supported Node executable, fixed argument array and no shell; scrub NODE_OPTIONS/preloads/debug options and credential-bearing environment. Use the already approved runtime alias `typescript-analysis` at exact TypeScript 6.0.3; keep the 7.0.2 check compiler. No target module/config execution, no emit/network/filesystem fallback from the virtual compiler host. Worker startup may load its own installed modules; this is not an OS sandbox or proof against arbitrary hostile native code.

Worker transport accepts one framed, schema-checked immutable input up to 32 MiB encoded UTF-8 and one result up to 16 MiB, with at most 64 KiB non-source diagnostic stderr (excess terminates with an output-limit result). Structured encoded limits supplement the 4 MiB source and 2 MiB metadata bounds, since escaping expands JSON. Cap V8 old-space at 256 MiB; this is a heap setting, not a measured RSS or total process guarantee. Enforce a 20-second wall deadline from spawn intent through result/exit, then bounded owned termination observation. Record resource/timeout failure without facts; signal sent alone is not confirmed cancellation. Do not block the parent on parsing unbounded IPC. Actual crash/OOM/timeout/cancel/oversize behavior must be exercised before acceptance.

On restart, unclaimed queued work is safe to claim once. In-flight context/worker work with no durable definitive outcome becomes unknown; no automatic replay. Owner-run generations fence late replies. Reconcile verified process ownership without killing reused PIDs; unknown possible-live work retains the global effect lease. Explicit new RequestAnalysis after quiescence is the retry, with a new generation/job, never a hidden replay. Already admitted result+receipt reads back without Git/compiler launch. A transactionally retained verified corpus/inventory and no claimed next invocation may continue its next distinct phase; a claimed-but-unfinished phase may not. A result-ready file/message without authoritative admission is not trusted success and requires explicit fresh analysis after recovery.

Prefer authoritative bounded SQLite corpus/result records admitted via source/worker witnesses; raw files are optional staging, not a second source of truth. If staging is necessary, use a separate `analysis-result-v1` owner-generated artifact registry/directory with exclusive restrictive temp writes, digest/length, atomic rename and verified same-descriptor reads. Never accept a caller path/URL, traversal or symlink. Import-artifact schema cannot be relabeled. Limit total retained encoded semantic corpus/results/inventories per review to 64 MiB, independently of source-import retention (whose current64MiB quota measures compact JSON source arrays, including duplicate occurrences and escaping); reject new admission at the cap without evicting evidence used by history/clarifications. Deduplicate identical immutable records by identity only after full-value equality; same ID/different content conflicts. Quota accounting sums UTF-8 byte lengths of canonical JSON bodies of distinct immutable corpus, declaration-inventory and analysis-result records for the review. Sort object keys recursively, preserve array order, and include source text, provenance, metadata and facts; job/generation references do not charge the same immutable body again. This is not a total database-size guarantee. Exact boundary passes and one byte over rejects new records atomically. Owner test constructors may lower, never raise, quotas. Cleanup removes only reconciled owner staging, never admitted SQLite evidence.

## React selection, source return and receipt confirmation

The semantic bridge owns a private snapshot and optional admitted analysis pin, separate from the server's selectedAnalysisId/currentSnapshotId. Opening exact source pins its analysis; later facts offer an explicit latest-analysis navigation action rather than replacing inspected evidence. Source/graph focus never changes the legacy question anchor or draft. Returning restores the originating control and scroll position. The source inspector slices exact UTF-16 offsets; it does not translate context into an invented line-only question anchor. Function/module contexts can share path/side/line ranges, so accessible controls identify name and kind too.

Preparation and admitted facts remain separate during new context or declaration choice. Background polling cannot replace explicit login, command readback or source navigation; credential/review/snapshot/analysis selection epochs fence late responses. Exact pending command identity remains recoverable across private navigation within the credential; changing an uncertain intent does not silently issue another command. Logout/replacement/disposal aborts owned reads and removes routes. A body excerpt loader owns at most one background batch and checks the still-selected corpus before publication.

The server minimumJobRevision belongs to the explicitly chosen historical analysis job when analysisId is supplied; otherwise it belongs to the latest requested generation's job. A delayed accepted receipt may refer to a different older job after a newer request. Confirm that receipt by its exact jobId in the authorized snapshot jobs collection, requiring that job's committed revision to reach the receipt minimum and its review/snapshot to match. The view's analysisGeneration is the snapshot's latest requested generation even with a historical analysisId pin; the receipt's analysisGeneration is that snapshot generation at command commit. The readback view must reach that generation. A job's generation is its immutable request generation: RequestAnalysis and SelectAnalysisDeclarations receipts share it, but CancelAnalysis can accept an older unknown job under a newer snapshot generation. For cancellation, preserve and match the captured job generation when known, and never require it to equal the receipt's newer generation. Do not apply an old job minimum to the latest job or assume a large unrelated revision satisfies it. Preserve a held historical analysis through an independent facts refresh with its private pin and graph minimum.

Command submission and accepted-receipt readback are separate phases. A later readback failure, including a definitive HTTP400, does not prove an already accepted command was rejected and cannot clear its original commandId/retry identity. ## Change, reason, goal and test graph decisions

### Change is the comparison subject

A Change is an identity-bearing graph subject with `before` and `after` relationships to the old/new behavior subgraphs or supported absence. It need not duplicate an entire unchanged call graph on each side. Shared context is retained with its actual identities and evidence; this does not merge revision-specific occurrences. ### Reasons, goals and intent

- A Change may be `motivated_by` a Reason and `intended_to_achieve` one or multiple Goals. A reason is not automatically a goal or an executed result.
- For an obstacle Reason X and Goal Y, store `X impedes Y`. Reading “Y is impeded by X” is a derived inverse, not a second duplicated assertion. A positive requirement is not the obstacle: here the obstacle is always constructing Bearer headers, not the desired absence of Authorization on an owner request.
- Removing an obstacle does not prove achievement of its goal. The goal “open the review without manual token entry” remains intended behavior until supported outcome evidence exists. Explicitly sourced intent, attributed interpretation and source-derived inference retain their provenance and review-confirmation status independently; confirmation is not execution.
- Optional intermediate intents are useful only when explanatory and supported. No forced tree, mandatory intent hierarchy, unsupported `requires` chain or author-edit-order/causation follows from graph adjacency.

### Tests and their changes

A test can change, remain unchanged, be new or be deleted. A test Change uses the same Before/After comparison-subgraph model and may be `motivated_by` the code Change. Added/deleted tests retain explicit supported absence, not fabricated old/new test definitions. An unchanged test retains its verification relation with no invented Change.

A test **verifies a specific behavior/assertion**; it does not automatically verify an entire Change, goal, security claim or PR. TestDefinition and its expected/asserted behavior, actual TestRun, result and supporting execution Evidence are distinct. Source discovery or a before/after expected assertion does not establish PASS or even that the illustrative test exists.
