# Product roadmap

**Direction:** Accepted progressive delivery: 480p → 720p → 1080p → 4K

**Plan status:** Slice sequence and dual-host/reactive refinement independently reviewed; later contracts remain provisional; no implementation started

**Owner:** Project maintainer owns product decisions; implementing agent owns delivery and evidence

**Schedule:** Ordered outcomes; no dates committed

**Authorization:** Documentation only. Probe execution, application implementation, installation and deployment are not authorized by this plan.

## Goal and current gap

Deliver the [vision](../vision.md): a reviewer can explain changed behavior, trace its consequences and justify a decision with evidence. The [high-level design](../architecture.md) defines the required boundaries. This repository contains documentation only. Host integration, application behavior, source analysis, execution and comprehension are unverified.

Every product slice must be dogfoodable using our own real PR; the [mandatory dogfood protocol](own-pr-dogfood.md) defines candidate identity, pinned target provenance, observations and revalidation. This accepted requirement applies from slice 01, not only to maturity work.

Each round contains independently testable vertical slices. Each slice adds a useful action to the running review journey and verifies its own outcome without waiting for later slices. “480p → 720p → 1080p → 4K” describes increasing fidelity and maturity, not screen resolution. Early breadth and polish may be limited; identity, immutable source provenance, permissions, durable outcomes and explicit unknowns may not be simulated away.

## Existing-work adapter requirement

[Codex and Claude](../participant-adapters.md) are both required participants for 480p. Attach from the already-running session in the current clone; that initiating session is the destination. Slice 01 has independently testable **01-Codex** and **01-Claude** deliveries with the same own-PR task. Each requires its own passing host probe and actual session evidence. One integration may proceed independently while the other remains pending, but full 480p completion requires both and slice 02 continuation for each. This does not introduce simultaneous multi-agent ownership.

The [functional/reactive direction](../reactive-design.md) is accepted; library selection is a later bounded implementation decision and does not enlarge the host probe.

## Gates before product delivery

1. Resolve the host/run-target inputs in the [host contract probe](probes/00-host-contract.md). After separate execution authorization, use the probe to establish actual binding, supported MCP, invocation deduplication and uncertain-outcome reconciliation. This is a feasibility experiment, not a product slice; it requires no product UI, graph, PR importer or comment domain.
2. Before presentation implementation, select the real change and record the evidence-backed expected account and evaluation criteria in the [comprehension protocol](comprehension.md). Its proposed PR profile, evaluator and threshold are not user selections. Resolve the listed material choices before dependent work.
3. Refine and authorize [slice 01](slices/01-review-loop.md) using the probe evidence and evaluation packet. Host and comprehension preparation are independent documentation work; product delivery needs both. A failed or inconclusive probe does not unlock the responsible-agent loop. Independently authorized source work may continue, but cannot be called completion of that loop.

The following inventories establish order, scope boundaries and observable checks. All entries are **planned, unimplemented and unverified**. Slices 02–12 remain provisional until their predecessors supply evidence; create their individual documents before implementation, not an entire speculative hierarchy now. Every row inherits the architecture constraints, mandatory own-PR dogfood gate and common test contract below. Supplemental representative PRs cannot replace the own-PR run.

|---|---|---|---|
| **06 — Check a claim on the head.** Select a configured test target and inspect its actual outcome while review continues. | Slice 05; selected repository runner/target, authorized execution environment and isolated worktree contract. | Same target/result identities through UI and CLI; durable test job; command/job/cancel separation; content/dirty-state/environment/command/artifact attribution. Tests cover cancel/exit races, lost launch acknowledgement and recovery by invocationId without blind retry. Reviewer distinguishes test presence, relevance and actual execution. |
| **07 — Compare the evidence.** Compare one claim on base and head and state what the difference establishes. | Slice 06; same configured target available on both sides; agreed comparison conditions. | Separate baseline execution worktree and results, actual source/environment differences, linked comparison artifacts. | **08 — Correct and enrich the shared explanation.** Challenge an interpretation, retain a correction and request a source-backed revision. | Slice 07; authorized enrichment scope; provenance and correction-retention contract. | User/agent shared permitted annotation actions, agent enrichment through durable ingress, source/interpretation/execution separation, subscribed terminal-job inbox events. ## Traceability and constraints across slices

| Vision / architecture requirement | First delivery and later refinement | Evidence boundary |
|---|---|---|
| Purpose and before/after behavior | 01; graph-led account in 04–05 | [Comprehension packet](comprehension.md) precedes presentation; transport success is insufficient. |
| Whole scope, supporting changes and dependencies | 03 coverage; 04 relationships; 05 exploration/story | Coverage, resolved source facts and reviewer understanding are separate checks. |
| Claims, tests and confidence with reasons | 01 source-backed reply; 04 related test source; 06 execution; 07 comparison; 08 enrichment | Static test presence is not execution, and successful execution proves only its bounded claim. |
| Durable conversation and corrections | 01 anchored question/reply; 02 continuation/history; 04 annotation; 08 correction retention | Exact actor, attachment generation, snapshot and reply must be proven, not supplied as trusted strings. |
| Commands, jobs and external effects | 01 ingress/receipts/turn delivery; 03 import job; 04 graph CAS; 06 test/cancel; 08 terminal-event wakeup | Short atomic transactions, separate jobs, turn-only serialization and stable invocationId remain required at first use. |
| Self-use on each delivered increment | 01–12, with [per-slice dogfood evidence](own-pr-dogfood.md) | Candidate provenance and reviewed baseline/head are separate; same-agent dogfood is not unfamiliar-reviewer evidence. |
| Orientation and realistic access | 01 readable labeled source/basic keyboard; 05 player; 09 density; 10 phone/assistive use; 11 recovery | Browser checks, human comprehension, physical device and screen-reader evidence remain separate. |

All domain writes use durable ingress; authorized reads use the query read model. Business rules belong to the responsible subsystem behind a public interface, not UI components. Transactions atomically commit state, receipts, events/outbox and relevant job creation, then end before external work. Agent MCP commands must progress during the agent's own serialized turn. Apply-time authorization/generation, action-specific concurrency and receipt-aware readback apply from the first relevant command. External invocationId is distinct from commandId; unknown outcomes are reconciled, never blindly replayed. Wakeups have explicit eligibility and durable inbox/consumption state. See the [architecture](../architecture.md) for the complete contract; deferred features do not weaken it.

All code must be tested, preferably through TDD. Each slice needs domain/interface tests and E2E for its actual user journey, using real decompozr/design-system integration. Record source version, environment, commands, artifacts, actual outcomes and limits. Simulations support only the boundary exercised. No fixtures, previous prototype receipts or document checks count as real-host, real-process, device or comprehension acceptance.
