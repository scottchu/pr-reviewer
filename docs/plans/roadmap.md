| Vision / architecture requirement | First delivery and later refinement | Evidence boundary |
|---|---|---|

| Claims, tests and confidence with reasons | 01 source-backed reply; 04 related test source; 06 execution; 07 comparison; 08 enrichment | Static test presence is not execution, and successful execution proves only its bounded claim. |
| Durable conversation and corrections | 01 anchored question/reply; 02 continuation/history; 04 annotation; 08 correction retention | Exact actor, attachment generation, snapshot and reply must be proven, not supplied as trusted strings. |
| Commands, jobs and external effects | 01 ingress/receipts/turn delivery; 03 import job; 04 graph CAS; 06 test/cancel; 08 terminal-event wakeup | Short atomic transactions, separate jobs, turn-only serialization and stable invocationId remain required at first use. |
| Self-use on each delivered increment | 01–12, with [per-slice dogfood evidence](../rules/own-pr-dogfood.md) | Candidate provenance and reviewed baseline/head are separate; same-agent dogfood is not unfamiliar-reviewer evidence. |
| Orientation and realistic access | 01 readable labeled source/basic keyboard; 05 player; 09 density; 10 phone/assistive use; 11 recovery | Browser checks, human comprehension, physical device and screen-reader evidence remain separate. |

All domain writes use durable ingress; authorized reads use the query read model. Business rules belong to the responsible subsystem behind a public interface, not UI components. Transactions atomically commit state, receipts, events/outbox and relevant job creation, then end before external work. Agent MCP commands must progress during the agent's own serialized turn. Apply-time authorization/generation, action-specific concurrency and receipt-aware readback apply from the first relevant command. External invocationId is distinct from commandId; unknown outcomes are reconciled, never blindly replayed. Wakeups have explicit eligibility and durable inbox/consumption state. See the [architecture](../product/architecture.md) for the complete contract; deferred features do not weaken it.

Every slice that introduces or changes a cross-subsystem stream must declare it through the managed integration layer, record its owner/scope and teardown, and test route boundaries, authorization, duplicate registration, cleanup, errors and slow-consumer behavior. Own-PR E2E inspects the relevant subscription diagnostics. No scattered direct subscriptions or hidden feedback loops are accepted; see the [reactive integration contract](../product/reactive-design.md).

All code must be tested, preferably through TDD. Each slice needs domain/interface tests and E2E for its actual user journey, using real decompozr/design-system guidelines and design principles. Record source version, environment, commands, artifacts, actual outcomes and limits. Simulations support only the boundary exercised. No fixtures, previous prototype receipts or document checks count as real-host, real-process, device or comprehension acceptance.
