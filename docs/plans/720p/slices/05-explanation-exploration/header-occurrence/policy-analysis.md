## Current source and model

## Options (proposals, no chosen implementation)

| Option | Exact source-level meaning | Required change / limit |
|---|---|---|
| 1. Test contains Assertion plus Test references declared policy | Test syntax owns these exact assertions; a source comment explicitly refers to a policy document/section. | Recommended. Retain contains. Add a separately evidenced source-reference relation only after extracting the exact comment and resolving the versioned policy target. Do not use a semantic policy summary or title matching as the source target. Unresolved doc-section identity remains unresolved. |
| 2. Assertion expresses expectation, with attributed policy-clause mapping | The expression written in this assertion expects the shown value/predicate. A separately attributed mapping says which policy clause it concerns. | Richer and useful for a later chosen design. Preserve actual expression, subject syntax, operator/expected syntax and assertion identity. Do not infer request/helper coverage, universal satisfaction or pass; conditionals, loops and helper bindings need explicit source-chain evidence. Policy mapping remains interpretation unless explicitly declared in source. |
| 3. Keep verifies_policy with an explicit static verification-specification mode | This test is specified to check a policy, without saying it passed. | Small surface change but weakest factual contract: current whole-test/source-interpretation basis and bundled policy still hide clause granularity. A label alone does not repair unsupported source-to-policy attribution. Not recommended for the lowest factual projection. |

Recommendation: choose option1 for the lowest-level layer. The indisputable facts here are lexical containment and the authored policy reference. Option2 may later connect those facts to richer expectation/policy interpretation without changing their identities. A static test can be designed to check a policy while failing, being skipped or never executing; that distinction is semantic, not a requirement to ingest CI now. Execution observations must separately link an actual run to the same pinned test identity and preserve environment/result provenance. No proposed static edge may acquire a successful-result meaning from a test file or a green CI badge alone.

Decision needed from Scott/owner before implementation: should the low-level graph show only the explicit authored policy-document reference (option1), or also an attributed assertion-to-clause interpretation (option2)? The current verifies_policy relation remains unchanged in this candidate as requested; this analysis is a proposal, not an accepted rename or expanded scope.
