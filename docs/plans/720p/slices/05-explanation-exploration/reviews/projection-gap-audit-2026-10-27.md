## Where the chain broke

**Specification translation.** `docs/product/review-loop/semantic-graph.md:166–168` at `9b74ed9` says Change compares Before/After behavior, shared context need not be duplicated, and the function remains named `request()`. Lines 187–191 separately protect revision-specific locations and anchor granularity. Those statements do not require two visible functions. However, the durable text did not explicitly define one request comparison projection, its exact occurrence pair or its display cardinality. The latest user correction resolves that presentation expectation; it must now be explicit in the owning projection contract. This audit cannot prove a deliberate override of a verbatim original design that is absent from the inspected packet.

**Handoff.** Minimal compilation packet `4bba542` deliberately selected JSON-visible nodes/edges and preserving canonical function IDs. The later v6 packet required nested Change graphs, File links and actual test links; it did not add one-request display mapping. V7 `9b74ed9` correctly requests kind-selected simple rows and graph preservation, but its first committed form still lacked the single-subject gate. Preserving two canonical occurrences was allowed to determine the view by default. Root owns that incomplete translation and dispatch scope; the implementer owns the direct one-record/one-card choice.

**Implementation.** The one-to-one map is a verified causal mechanism, not a motive: both request records enter `allEntities()`, and each becomes a ReactFlow node. The renderer has no comparison adapter that can preserve both records while presenting one subject. A plain node title change cannot fix this; neither should the semantic records be collapsed or renamed to force a visual result.

**Tests and review.** Pure tests establish selected evidence fidelity; browser tests establish literal JSON, group presence and representative geometry. Those were useful but did not ask the user's comparison question. My prior source review accepted the bounded three-gate data structure without identifying this missing projection contract. Its no-blocker conclusion was not evidence that one visible request subject had been achieved. Root must not promote those bounded passes into the desired overall outcome, and reviewers must test that outcome explicitly rather than infer it from preserved IDs or successful rendering.

## Verified causes versus inference

Verified: direct entity-to-card mapping, absent comparison-display mapping, generic JSON renderer, tests tied to literal JSON/card count, and missing explicit one-request gate in the inspected handoffs. These explain the observed structural output without assuming intent.

Inference: emphasis on canonical-ID preservation and local hard gates likely encouraged retaining the source-record inventory as the display. That is a plausible coordination explanation, not demonstrated author intent or a reason to discard source identity.

Raw JSON also needs an honest chronology: the earlier packet explicitly authorized JSON inspection. It is not accurate to retroactively call all old JSON rendering unauthorized. The current simple-row request supersedes that presentation choice; continuing it afterward would be a failure to reconcile the new expected outcome. The historical static mockup's visual failure and source/schema checks never adopted it as a readable final UI.

## Small preventive contract for this correction

1. Preserve **X**: exact graph IDs, revision occurrences, nesting, relations, evidence, both File anchors, actual modified-test relevance and not-run status. Strip **Y**: diagnostic fields from normal visible rows, duplicated request subject cards and unwanted chrome. Record the distinction before changing the renderer.
2. Give the local projection one explicit prepared pair: requestBefore canonical ID plus requestAfter canonical ID → one display subject. Reject an incomplete/mismatched pair; do not generalize to name-based matching. Display edges retain their originating semantic relation/version and map endpoints through that declared pair.
3. Verify semantic equality separately from view outcomes: unchanged serialized graph; one request card; Before constructs and After calls branches; both exact short-commit/range File links; real modified test and indirect/not-run status. No count-only substitute.
4. Review desktop/390 ordinary reading: no visible diagnostic dump; known kinds have rows independent of labels; full Before/After edge-card colors; every child and external card clears the purple boundary; a reader can follow the two branches and locate both source sides. Preserve failed evidence and stop calling the affected outcome passed until it is observed.

These are focused assertions and review tasks in the existing local projection seam. They do not require a new framework, generic registry, panels, source-model migration or runtime/owner work. The executor's ongoing correction remains authorized and should continue; this audit does not pause it or claim that its moving implementation has passed.

## Latest user correction supersedes the request-only recovery

The user subsequently clarified the general requirement: each logical entity (including file, function, variable and test) has exactly ONE graph node, with source-comparison status change/nochange/add/remove. This applies across the current prepared graph, not just the request card. Root explicitly authorizes correcting the normalized prepared output while keeping original source packets/anchors immutable. The earlier byte-equal-output constraint and request-only display adapter are therefore insufficient as the final recovery; do not silently promote them into acceptance.

The deeper specification gap is concrete. The ontology distinguishes logical Symbols from revision-specific occurrences (`project-repository-ontology.md:15–20` at `9b74ed9`), but did not compile that distinction into required logical-node identity, complete occurrence mapping, graph cardinality and status rules. `minimal-graph.ts` instead makes `request-before`/`request-after`, side-specific File records and two test definitions separate entities. Its `GraphEntity` shape does not require logical identity or comparison status. The renderer then faithfully reproduces that incomplete output. Canonical-ID retention tests and the fixed 16-card assertion enforce record retention, not logical-entity uniqueness. This is an input/model contract omission as well as a projection omission; changing one request title/card cannot fix it.

The next bounded review must cover **all currently prepared entities**: exactly one logical node per evidenced entity; explicit mapping to every retained Before/After occurrence; status justified at the declared source granularity; and relations carrying both exact side/File anchors without duplicating the logical File or test subject. Preserve Change graphs, nesting and actual indirect test relevance. Do not infer logical identity merely from equal names or basenames, and do not expand to unprepared whole-PR analysis to satisfy a count.

Status must describe what the evidence proves. Equal refresh body bytes justify source nochange, not unchanged downstream behavior. Removing an inline Bearer expression does not prove Authorization disappeared from every After path. Non-Git Reason/Goal entities need an explicit status/applicability basis rather than guessed revision history. Missing mapping/status evidence is a documented unresolved item, not permission to fabricate a pair or silently drop a required entity.

Preventive acceptance therefore changes from “one request card plus unchanged old graph” to “one normalized logical node per current entity, truthful status and exact immutable occurrence/evidence mapping.” Tests and independent review must check that model contract before visual row/cardinality checks. This correction remains header+graph only, with no new framework, panels or owner/runtime changes.

## Actual automation boundary and missing relation derivation

The current candidate is not an end-to-end automatic PR-to-understanding compiler. Verified layers are different:

| Layer | Actual mechanism / evidence | Limit |
| --- | --- | --- |
| Pinned source | `prepare-source.ts:9–15` reads Git objects and checks SHA256. | This verifies source bytes; it does not derive the explanatory graph. |
| Syntax and static analysis | `prepare-context.ts:19,50` walks a TypeScript AST; `src/source-analysis/analyze.ts:181` builds a TypeScript program. | A parser/compiler exists, but its existence does not mean every current graph fact was statically resolved. The current client packet has zero admitted static edges and 16 explicitly source-observed manual relations. |
| Representative knowledge | `core-request-graph-v1.json.membership.selection` explicitly declares a curated request-header seed and bounded membership. | Test relevance, rationale and logical-entity correspondence are prepared knowledge with source support, not demonstrated general automatic inference. |
| Logical compilation | `comparison-graph.ts:1–7,61–84` reads an explicit mapping and remaps the hand-selected `minimal-graph.ts` graph. | This normalizes the supplied shape; it does not automatically compare every canonical relationship on both sides. |
| Rendering | `minimal-main.tsx` renders the compiled records through the row projection. | Rendering cannot recover a supported relationship dropped earlier. |

The refresh case demonstrates the missing step exactly. The immutable core already contains a Before refresh→request call at line37 and an After call at line38, both exact source-observed records. `minimal-graph.ts:45` selects only `headRefreshCall`, and `:111` emits only its After relationship. `comparison-graph.ts:84` copies/remaps those selected edges rather than deriving relationship comparison from the core calls. Thus unchanged source-call context can appear After-only, inviting a false reading that it is new.

The bounded correction is to derive relationship comparison from those **existing canonical Before/After records**, using the explicit occurrence-to-logical-subject mapping and evidenced callsite correspondence. The paired refresh call should retain both original sites/provenance and a source-scoped no-change relationship status. The new helper call has separate head-only/add evidence; removing direct inline header construction has scoped removal meaning. Relationship comparison status must be independent of provenance version. This requires no new parser, dependency, whole-PR discovery or broad identity algorithm.

Adding another handpicked Before arrow may fix one image but does not close this derivation gap. The acceptance check should remove that special selection and demonstrate that the bounded core input deterministically yields the paired relationship, with original IDs/sites and honest frontier. Documentation must keep this capability separate from curated seeds, manual source review, prepared test relevance and intended outcomes.
