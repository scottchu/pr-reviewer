# Working in PR Reviewer

- Keep repository content in English.
- Use docs/README.md as the documentation map: docs/product/ holds durable product knowledge, docs/rules/ holds shared workflow rules, and `docs/plans/<round>/` holds that round’s plan, slices, probes and review records. Keep each slice’s plan and any handoffs/reviews/evidence together in its own directory; do not split related work into global type-based folders.
- Treat docs/ as the repository source code and authoritative specification. The agent derives and compiles all other project artifacts from it, including application code, tests, schemas and configuration. Follow docs/rules/documentation.md for the documentation-to-delivery contract.
- Before changing derived artifacts, update the relevant docs with accepted intent, decisions and slice acceptance. Trace implementation and tests to those docs; return findings, evidence and corrections to docs as work proceeds. Do not let chat or implementation become a competing source of truth.
- Use strict TypeScript for application code and tests. Derive compiler configuration from the accepted slice when implementation begins, without introducing a scaffold early. No lint/format tool is selected or required yet.
- Prefer arrow functions. Use function declarations only when required.
- Prefer functional patterns over classes; classes are allowed when justified by their responsibility. Follow the implementation conventions in docs/rules/development.md.
- Design specifically for React with clear subsystem boundaries. There is no framework-agnostic core, reusable SDK or alternate-framework support requirement; do not add abstraction layers or package splits solely for hypothetical portability.
- Choose React patterns according to the actual requirement; no particular component customization pattern is prescribed. Preserve accessibility, decompozr/design-system guidelines and design principles and subsystem boundaries.
- Prefer a functional core with explicit immutable inputs and reactive coordination at effect boundaries; keep business policy out of UI and stream operators. Follow docs/product/reactive-design.md; no reactive library is selected yet.
- Route all cross-subsystem streams through the declared integration layer and managed subscription registry. Never directly subscribe to another subsystem’s internal modules/streams. Centralize wiring, ownership, teardown and diagnostics; keep routes scoped, authorized, bounded and independently observable.
- Support Codex and Claude participants from their existing work sessions. The session initiating attachment is THE attached session; never silently create, fork or replace it. Follow docs/product/participant-adapters.md for independent host evidence and ownership boundaries.
- All code must be tested. Prefer test-driven development (TDD).
- Dogfood every product slice using our own real PR before accepting it. Follow docs/rules/own-pr-dogfood.md: record the task, candidate build/source identity, pinned reviewed base/head, observed evidence and gaps; rerun affected checks after fixes. Same-agent dogfood does not establish unfamiliar-reviewer comprehension.
- Isolate each subsystem with clear responsibilities and explicit public interfaces. Access other subsystems through those interfaces rather than their internal implementation.
- Keep business logic in the responsible domain or application layer. UI components present state, collect user intent and delegate operations through those boundaries; do not concentrate business rules in UI components.
- Include end-to-end tests for implemented user journeys. Use decompozr/design-system guidelines and design principles to guide React UI. Do not use Svelte or its component package. End-to-end tests cover the actual React user journey; visual review checks the guidelines separately.
- Name new branches descriptively without a `codex/` prefix. Do not rename existing branches solely for this preference.
- Make changes and commits on task branches in isolated worktrees. Never commit directly to main or push directly to main.
- Every change must enter main through a GitHub pull request. Do not merge task branches directly into local main. After the PR is merged, refresh clean local main only by fast-forwarding from origin/main.
- Build the project from the top down: vision, product goals and user experience, requirements, system design, then implementation. Develop and commit each meaningful step as it is discussed; do not generate the whole documentation hierarchy in advance.
- Keep all project plans and individual slices in Git-tracked docs/plans/. Link slices to their parent plan and record scope, acceptance, testing, progress, evidence and unresolved gaps. Do not keep plans or slices in .decompozr/ or only in chat.
- Maintain roadmap → round plan → individual slice plan for every delivery round. Create each round page when planning that round and each slice page before implementation; keep later scope provisional rather than generating the entire hierarchy in advance.
- Every product slice needs a versioned implementation handoff and independent-review handoff in its tracked plan, following docs/rules/agent-handoffs.md. Supply each assigned agent the committed packet and exact role/scope; chat is dispatch, not the specification. Missing readiness inputs block the affected work, not independent preparation.
- Before accepting every slice, promote learned behavior, user stories, UX, high-level architecture, low-level design decisions, interfaces, rationale and verified limits into durable product docs outside docs/plans/. Plans are transient delivery coordination/history, not the sole product specification. A fresh agent must be able to reimplement accepted delivered behavior from maintained docs without old plans, chat or application code; see docs/rules/documentation.md.
- Before accepting a slice, reconcile implementation evidence and independent review findings into its plan and update every directly dependent slice plan with delivered interfaces, evidence, limitations, changed assumptions and remaining gates. The successor reconciles those inputs before implementation; predecessor completion is not automatic successor readiness.
- Start with README.md and AGENTS.md. Add documents under docs/ gradually, beginning with the vision. Keep README user-facing and put agent workflow rules here.
- Separate dates, statuses, and technology layers into clearly labeled entries. Do not compress them into one sentence.
- Carry prior user decisions as context, while distinguishing accepted direction, proposals, observed evidence, and unknowns. Later user corrections take precedence.
- Do not restore the previous application or introduce dependencies, build output, or a technical scaffold before its implementation scope is established.
